# Issue M9-010 — Implement telemetry publication on the device

**Milestone:** M9 · **PRD:** [PRD 090](../../prd/090-esp32-rust-firmware.md) · **Depends on:** M9-009

## Context

Protocol sections 5.1-5.5, published from fake sensors in M9 so the pipeline
is proven before real hardware is involved.

## Goal

Publish telemetry and status from the device.

## Scope

- Soil, tank, weight, and pump telemetry from the fake adapters
- Envelope with UUIDv7 when synced, v4 when not
- Monotonic `sequence` within a boot
- QoS 1, **retain false**
- A 16-sample ring across disconnects
- Status heartbeat every `5 x telemetry_interval`
- Sensor error counters in status

## Non-goals

- Real sensors (M10).

## Dependencies

- M9-009

## Implementation notes

The telemetry ring is bounded at 16 because a device is not a ledger for
samples and unbounded buffering exhausts a 400 KB heap. Command results are the
exception and are handled separately (M9-011).

Publishing a `null` field on a read error rather than the last good value is
what makes staleness and stuck detection work upstream.

## Acceptance criteria

- [ ] All configured telemetry kinds publish with valid envelopes.
- [ ] `retain` is false on every telemetry publish.
- [ ] `sequence` is monotonic within a boot.
- [ ] UUIDv7 when synced, v4 with `clock_synced: false` otherwise.
- [ ] At most 16 samples are buffered across a disconnect.
- [ ] Status heartbeat appears on schedule with sensor health.
- [ ] Fixtures generated by the firmware match the corpus.
