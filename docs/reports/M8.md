# M8 — End-to-End Test Environment

**Status:** DONE — 2026-09-02. M8-001 through M8-018 and every PRD 080
acceptance criterion were demonstrated against the real Docker topology. M9 is
READY and has not started.

## Delivered

The whole software system — Mosquitto, the device simulator, the edge
controller, the cloud API, and PostgreSQL — starts from one
`docker compose up --build`, and the complete scenario suite runs against an
accelerated copy of it from one `./scripts/run-scenarios.sh`.

Three multi-stage Dockerfiles build the services with `cargo chef` dependency
caching onto `debian:bookworm-slim`, each running as uid 10001 with the binary
as PID 1, so `docker compose stop` delivers SIGTERM to the process and the
graceful-shutdown path runs. Health gating is by HTTP against what each service
is actually serving.

`deploy/docker-compose.test.yml` overlays an accelerated topology: every service
has `restart: "no"` so a crash fails the run instead of being papered over, the
edge and both simulators take one `RHIZO_TIME_SCALE`, and the edge image is
built separately, and tagged separately, with the `e2e-faults` feature that
compiles in the two process-boundary crash hooks SCEN-051 and SCEN-102 need.

`rhizo-scenarios` is a Rust binary with a typed harness: an edge REST client, a
simulator control client, direct SQLite and PostgreSQL readers, an MQTT spy
subscribed to `rhizo/v1/#`, Docker lifecycle control, per-scenario database
reset, and a failure dump of database rows, captured MQTT, simulator state, and
container logs. **Forty-one scenarios** cover the baseline, MQTT and device
failures, lockouts, restarts, cloud independence, isolation, reconciliation,
battery and sleep, the rolling-cap boundary, and the eighteen-step first demo.

Three startup checks run before the first scenario and end the run on failure:
time-scale agreement across edge, simulator, and runner; that the edge under
test can actually be crashed at an exact instant; and that each device
authenticates as itself rather than as the edge principal.

## Mutation verification

All seven mutations turn the suite red; the full record, including the exact
failure each produced, is in
[mutation-verification.md](../testing/mutation-verification.md).

Three were **green on the first attempt**, and each was a genuine weakness:

- **Staleness (2).** SCEN-022 withheld the soil stream, which stops the device's
  clock and the edge's receipt together — so a build dating samples by
  `device_time_ms` aged them out on the same schedule as a correct one. The
  scenario now skews the device's clock a day ahead before the stream goes
  silent, and the mutation is caught.
- **The rolling cap (5).** No scenario approached the daily cap, so the window's
  shape was untested; `scenario_rolling_cap_across_midnight` fills the allowance
  and crosses a virtual midnight. It was *still* green afterwards, because
  `budget::window_start` — the function that documents SAFETY-006's window — was
  called by nothing outside the domain crate's own tests, while the control loop
  and the plant API each recomputed the window inline. Both now go through it.
- **The shared validator (6).** Caught by SCEN-042 rather than SCEN-040: the
  edge's gate refuses a leaking plant before a command is published, so the
  device's own refusal is never reached. The tank case does reach it. Nothing
  needed changing; the record did.

Mutation 3's detection is blunter than PRD 080 implies — a blocking drain stops
the edge binding its API at all, so the run fails at the first startup check
rather than inside SCEN-060 — and is recorded as such rather than dressed up.

## Flakes, found and fixed rather than retried

Five scenarios failed intermittently before the three clean runs above. None was
retried; each was a scenario asserting something subtly different from what it
claimed, and the accelerated clock is what made the difference visible.

- **SCEN-011** opened its quiet window as soon as an acknowledgement appeared on
  the wire. That is the edge having *sent* one, not the device having consumed
  it, and a republish already in flight still arrives. It now waits for the
  device's own ledger (`pending_results`) to empty, drains, and only then
  observes.
- **SCEN-012** sampled the telemetry count at the instant the broker stopped.
  Stopping the broker ends delivery; the messages already in the edge's
  ingestion channel are still its to commit, and at 3600× that drain is hours of
  virtual time. It now waits for ingestion to settle and then asserts an exact
  equality, where it previously tolerated one unexplained batch. Its retained-
  status check was a single sample of a message that arrives on the spy's own
  reconnect, and now waits for it.
- **SCEN-022**'s quiet window began when the fault was injected rather than when
  the lockout appeared. The last reading is still fresh at that moment and the
  plant is still dry, so an edge that dosed then was behaving correctly.
  SAFETY-005 is about acting on data that has *aged out*.
- **SCEN-051** cleared the MQTT spy before restarting the edge, so its "exactly
  one command was ever published" window covered only the second process
  lifetime — where the right answer is zero, not one. It now spans both.
- **SCEN-114** paused the device while it set up each variant. A paused device
  publishes nothing, so its readings age out, and `max_sample_age` is a quarter
  of a second of real time at this scale. The gate is ordered, so stale inputs
  answered `uncertain` before it reached the leak, the tank, or the cap —
  correct behaviour about the wrong subject, and a different variant failed each
  run. The pause bought nothing the sleep did not already give, and is gone.

### Six more, found 2026-09-03 the first time the suite ran on a runner

**This section was written before the suite had ever completed in CI.** Every
`End-to-end` run until 2026-09-02 died in setup after ~25 s, so the flakes below
were fixed against a 32-core developer machine and the suite had never met a
2-vCPU runner. M9's commit fixed the setup failure, the suite finally executed,
and six latent races surfaced — one per CI round trip, which is the expensive way
to find them.

| Scenario | The assumption that only held on a fast machine |
|---|---|
| `normal_telemetry` | Read a batch count, stopped the publisher, re-read, and demanded the same number. Stopping a container is not instantaneous and an in-flight batch still lands. **Unprovable as written**; now asserts batch atomicity on a settled snapshot |
| `rolling_cap_across_midnight` | Assumed "crossed midnight" implies "under 24 h elapsed". Diagnostics showed 24.315 virtual hours — the rolling window had legitimately released the dose. **The edge was right**; the scenario now approaches the boundary deliberately |
| `history_gap` | Budgeted in *poll iterations*, which is ~60 s on a desktop and ~330 s on a runner; and its 72-real-second isolation ceiling expired before the buffer filled, flushing the ring and making the predicate permanently unsatisfiable. Now a wall-clock deadline under a ceiling that outlasts it |
| `sleep_budget_cooldown` | An unbounded `loop` with no budget and no message. Now bounded, and it reports its last observed state |
| `duplicate_replay` | Read the MQTT capture immediately after the device reported `connected`, but a device replays *after* connecting. Now waits for protocol §5.4's `complete: true` marker |
| `battery_awake_cycle` | Exposed a **real edge defect**, not a test problem — see below |

**The one that was not a test problem.** `battery_awake_cycle` failed about one
run in two, and the edge's own log said why: `a held dose was refused at
delivery … reason: "uncertain"`. That is the reconciliation hold (SAFETY-016),
and a battery device reconnects on *every wake*, so for it the hold is a routine
momentary state rather than a verdict. `control::intents` treated it as terminal
and discarded the operator's request. It already drew exactly this distinction
for `clock_unsynced` — "the window itself is bounded" — and `uncertain` belongs
in the same set; it is there now. **Nothing at the gate was loosened**: the full
gate re-runs on every delivery attempt, and leak, low tank and the daily cap stay
terminal.

**The lesson worth carrying.** These were not fixed by widening budgets. Four of
the six were *missing synchronisation barriers* — a scenario asserting on a
snapshot where it needed to wait for an observable event — and one was a budget
expressed in the wrong unit. The way to find the rest before CI does is
`docs/testing/local-development.md` §14: pin the containers to two CPUs so
`nproc` inside them matches a runner. Loading the host's cores instead
reproduces throughput but not concurrency, and invents failures that CI cannot
have.

Result: **41/41 in 532 s on a runner** (`End-to-end` 33732498713), the first
green end-to-end run in the project's history.

## Defects found and fixed

The assembled system found things the unit suites could not. In rough order of
severity:

**A lost update between the control pass and the result pipeline.** The pass
reads a plant's state, evaluates the pure machine, and writes the result; a
`command.result` settling the same plant in between makes that write stale. The
observed sequence: a dose settles, the pipeline moves the plant
`dose_issued → wait_for_absorption`, and the pass writes `dose_issued` back —
recording no transition, because from its own view nothing changed. The plant is
then held against a command that has already completed and the machine answers
`Wait` for ever. Fail-safe, and a plant that stops being watered until the
process restarts. Fixed with a single-statement compare-and-set
(`put_irrigation_state_if_unchanged`), with a test for the stale writer.

**The clock-step detector could never fire.** The edge's wall clock had become
`anchor + monotonic_elapsed × scale`, read once at startup — so
`clock_step::Detector`, whose whole method is comparing the wall clock against an
independent monotonic reference, was comparing it against itself. F-060-51's
forward-step lockout was unreachable at *any* scale, and NTP corrections could
never reach the edge or the devices it serves `edge.time` to. `HostClock` is now
two variants: production reads the host afresh on every call, and only the M8
overlay anchors.

**Device identity in the reference topology.** Both simulators authenticated as
`rhizo-edge`, whose ACL grants `readwrite rhizo/v1/#`. Every device therefore had
fleet-wide rights and ADR-012's `pattern readwrite rhizo/v1/devices/%u/#`
boundary was never exercised. Devices now authenticate as themselves, a
replica-aware entrypoint gives each `--scale`d instance its own account, and the
runner refuses to start unless it can *demonstrate* the boundary — by publishing
to a neighbour's subtree as the device and requiring the message not to arrive.

**`cargo test --workspace` hung forever.** `serve`'s loopback guard had been
deleted rather than gated, leaving its test awaiting a future that never
returns. The guard is back as `permit_bind`, checked at both the CLI and the
serving boundary.

**Process-boundary crash hooks were in the production binary**, reachable by an
environment variable and a file in the edge's own data directory — a
`std::process::exit` on the actuation path. They are now the `e2e-faults` cargo
feature, off by default, in a separately tagged image, with the runner asserting
at startup that the build it drives actually has them.

**The forward-compatibility of the simulator's state file had been inverted.**
The checksum had moved from covering the decoded state to covering the raw JSON,
so a field a future build added made a perfectly good file look corrupt — and
corruption disables actuation. Restored to hashing the decoded state.

**Transient `SQLITE_BUSY` surfaced as 500 from the REST API.** The edge has
three writers — the control loop, the ingestion pipeline, and the API — and
SQLite serialises writers even under WAL. The ingestion pipeline has retried
transient storage failures since M3; the API never did, so an operator's dose or
lockout reset could fail with a 500 because something else held the write lock.
`with_busy_retry` gives the operator paths the same bounded wait. Only
`StorageError::Busy` is retried, which `classify` already names transient, so a
constraint violation or an I/O error still returns on the first attempt.

**Smaller ones.** `GET /plants/{id}` reported `clearable: false` for every
lockout, contradicting the 409 body about the same plant. The overview endpoint
read `devices.connectivity_mode` raw rather than through
`connectivity::from_projection`, and returned `plants: []`. The
`clock_unsynced` lockout auto-cleared within one tick, so SCEN-025's "the lockout
names the specific remedy" was true for a fraction of a second; it is now held
for the refused command's own TTL. The `clock_unsynced` lockout and the
irrigation transition were written *after* the settling transaction rather than
inside it. `RHIZO_E2E_CLOUD_BATCH_SIZE` became the ordinary `cloud.batch_size`
setting. The irrigation pass skipped plants by `auto_watering_enabled`, which
defaults to `false` — so by default no plant's gate ran on the tick; it now skips
by the absence of an actuator, which is what SAFETY-018 actually says.

## Deviations from the plan

**The suite is not `up --abort-on-container-exit --exit-code-from
scenario-runner`.** That command cannot work here: the flag ends the run the
moment any container exits, and stopping containers is what a third of these
scenarios *do* — SCEN-051 kills the edge, SCEN-012 restarts the broker, SCEN-060
stops the cloud, and the harness stops the edge and simulator between every pair
of scenarios to give each a clean database. Measured, not assumed: under that
flag the runner is SIGKILLed with exit 137 during the second scenario.
`scripts/run-scenarios.sh` brings the topology up, waits on its health gates,
runs the runner as a one-shot container, collects diagnostics on failure, and
exits with the runner's status. PRD 080 §Interfaces records the amendment.

**The battery simulator is not behind a Compose profile.** Five scenarios need a
sleeping device, and a default topology that cannot run part of its own suite
would make the documented one-command run false. It exists only in the test
overlay, so the base topology still has no battery node.

**`scenario-runner` *is* behind one.** It is a one-shot process that stops and
starts the services around it; left in the default set, `up --wait` would launch
it alongside them and then fail because a container it stopped is not running.

**M8-013's mutation 5 is carried by a new scenario**, not by
`scenario_full_watering_cycle` as PRD 080 names — for the reason in the mutation
record. `scenario_rolling_cap_across_midnight` covers SCEN-034.

## Tuning that is not arbitrary

Two numbers in the overlay were arrived at by measurement and are commented
where they live:

- **The control tick is 120 logical seconds**, not the production 30. At 3600×
  the latter is a pass every 8 ms, and the control loop, the telemetry pipeline,
  and the REST API then contend for one SQLite file hard enough to exhaust the
  five-second busy timeout — the API starts answering 500. Every threshold the
  loop watches is far coarser than two virtual minutes.
- **The battery node wakes every 1800 logical seconds and stays awake for
  1200.** In real time that is 167 ms asleep and 333 ms awake. The awake window
  has to cover the whole delivery path — wake status reaching the edge, a tick
  noticing it, `edge.time` and the command going out, the device acting — and an
  earlier 900/1 pair gave *less than one tick* of it, losing the command about
  one run in three. The cycle length is bounded from the other side by SCEN-115,
  which needs about 190 of them.

Neither number changes anything a production deployment runs.

## Handoff

M8 is complete. **M9 is READY and has not started**; its first issue is
[M9-001](../issues/M9/001-verify-esp32-toolchain.md).

M9's first open question is answered empirically by that issue: whether stock
Rust 1.98.0 builds `riscv32imc-esp-espidf` or whether the espup channel is
required. The firmware is a separate workspace with its own toolchain pin
(ADR-001, ADR-007), so nothing in it can move this workspace's MSRV.

Two things M9 inherits from this milestone are worth carrying forward. The
`PENDING_RESULT_LIMIT = 32` ledger bound is a **simulator** constant and not a
specification — M9-011 decides the firmware's saturation behaviour on its own
terms, and M9-022 verifies it. And the eight exact device subscriptions are now
exercised end to end by a device that authenticates as itself; a firmware that
subscribed to `commands/+` would be refused by the broker rather than merely
being wrong.
