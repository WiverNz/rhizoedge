# M4 — Device Registry and Health

**Status:** DONE — 2026-08-28. M4-001 through M4-013 and the milestone exit gate were demonstrated.

## Delivered

- M3's single MQTT ingress/decoder remains the only transport path. Its durable status-order outcome gates registry projection; duplicates and logically old status cannot refresh `last_seen_at` or regress state.
- Every valid status receipt independently publishes live QoS 1, non-retained `edge.time`. A real-Mosquitto fresh-subscriber check proves it is not retained. The liveness timer refreshes online devices every 300 seconds.
- Registry rows hold lifecycle, firmware/protocol, boot, clock, config, resource, sensor, declared-capability, and advisory-connectivity state. Auto-registration records `device_registered` and creates no plant.
- LWT applies offline once, freezes `last_seen_at`, distinguishes `connection_lost` from `shutdown`, and records the transition. Boot changes are events/counters; rapid alternation raises `boot_id_thrash`.
- Staleness is derived from Edge `received_at` as `max(15 minutes, 3 × telemetry interval)`. A supervised timer detects silence without inbound traffic, emits stale/drift events, updates lifecycle gauges, and maintains time sync.
- Sensor presence/health/errors, row-based capabilities, capability changes, drift, isolation periods, and connected/isolated/reconciling state are exposed without assuming hardware.
- Axum serves health, metrics, device list/detail/name patch/events, and quarantine endpoints. It uses loopback by default, exact-origin CORS, bounded bodies/time, consistent errors, immutable device IDs, RFC 3339 timestamps, and bounded route/status metrics.
- Readiness requires MQTT `Subscribed`, tolerates one reconnect backoff, reports the pre-M6 control loop as `not_applicable`, and excludes cloud reachability.

## Post-M4 battery-compatibility correction — 2026-08-28

After the original M4 gate completed, the registry/health model was corrected
before M5 started so an intentionally sleeping battery device is not presented
as an ordinary failure. This is a dated correction, not a claim that the
original M4 implementation already contained battery support.

The additive MQTT v1 change is deliberately small: `device.status.data.power`
may declare `mode`, relative `wake_interval_seconds`, and diagnostic
`expected_wake_ms`, `wake_reason`, `battery_mv`, and `awake_ms`. Absence or an
unknown mode resolves to `always_on`. A sleep announcement is the existing
retained QoS 1 offline status with `reason: "sleeping"`; it is valid only with
declared battery mode and a 60–86400 second relative interval. No topic,
subscription, retention rule, consumer, decoder, or status-order path was
added. The device timestamp remains diagnostic and never drives liveness.

The complete internal state model is `Online`,
`SleepingExpected { expected_until }`, `OfflineUnexpectedly`, and
`Reconciling`. The established REST vocabulary maps these to `connected`,
`sleeping`, `isolated`, and `reconciling`. Edge computes
`expected_wake_at = received_at + wake_interval_seconds` and
`overdue_at = expected_wake_at + max(wake_interval_seconds, 300 seconds)`.
An accepted sleep does not refresh `last_seen_at` and emits `device_slept`, not
an offline-failure event. A timer-only missed deadline transitions to isolated,
increments `missed_wake_count`, and emits `device_wake_missed`. A newer wake
returns online, clears the window/count, and emits `device_woke`. M3's persisted
boot-generation/status-sequence decision remains the sole ordering authority;
duplicates and logically old receipts do not change registry state, while the
existing pipeline still publishes non-retained QoS 1 `edge.time` for every
valid receipt. A delayed LWT cannot replace an active valid sleep window, and
an older-generation LWT cannot regress a newer wake.

SQLite now persists the declared mode, relative interval, announcement receipt,
wake/deadline timestamps, and missed-wake count. REST exposes `power_mode`,
`wake_interval_seconds`, `expected_wake_at`, connectivity, and the count.
`devices_sleeping` and `device_wake_missed_total` are fleet-wide unlabeled
metrics; sleeping devices are excluded from the offline gauge. Measurement
staleness remains a separate Edge-receipt-time calculation and uses the battery
wake interval as its effective cadence.

Tests cover intentional sleep, duplicate sleep without `last_seen_at` refresh,
unexpected disconnect, timer-only missed wake, wake recovery, delayed LWT,
old-status ordering, conservative unknown mode, invalid/unbounded sleep, and
always-on compatibility. The live-Mosquitto integration additionally proves
that both the accepted announcement and its transport duplicate receive a
fresh, non-retained `edge.time` response.

The correction gate passed formatting, warnings-as-errors Clippy, the complete
all-features workspace suite, the required `RHIZO_REQUIRE_BROKER=1` suite
against live Mosquitto (including broker restart), both Thumb no-std builds,
SQLx prepare/check after applying all six migrations, docscheck (6,465 checks),
and `git diff --check`. Compose configuration was already demonstrated by the
original M4 gate and the Compose file is unchanged by this correction; the
literal re-check could not execute on this host because its `docker.cmd` wrapper
targets an absent `Ubuntu-24.04` WSL distribution. The running workspace
`edge-controller.exe` was stopped once because Windows held its output binary
open and blocked the requested Cargo gate.

Planning was reconciled without starting M5: M5-020 is superseded by this
correction; the minimal status portion of M5-019 is superseded while its battery
measurement/config remainder stays ready. M5-021 still owns simulator sleep.
M6-022/-023 retain durable pending-until-wake command intent delivery and forbid
retained water commands; M9-019…021 retain actual deep sleep, gated peripheral
power, and wake/publish/sleep firmware; M10-011/-012 retain measured sensor
stabilisation and system power draw; M12-018 retains “Sleeping — expected wake”
and “Pending until device wakes”; M14-009 retains optional solar/energy planning.

Final state remains: **M4 DONE · M5 READY · M5 not started**.

## Post-M4 independent review and correction — 2026-08-28

The battery correction above was re-audited against the code rather than against
its own report, together with the M3/M4 boundary it extends. Six defects were
found and fixed. Nothing in the section above has been rewritten: it records what
was true when it was written, and this section records what was wrong with it.

**The reported connectivity state was stored, not derived.** The API mapped
`devices.connectivity_mode` straight through and never compared `overdue_at` to
the clock, so an overdue sleeper read `sleeping` until the liveness timer next
ran — and, if that timer were stopped, panicked, or simply not yet started after
a restart, indefinitely. That is SAFETY-021's own failure mode reintroduced by
the mechanism meant to enforce it, and M5-020's superseded text had said
"derive, never store" for exactly this reason. `from_projection` now takes the
edge clock and the deadline; the column and the timer remain, because the timer
still owns the durable transition, its event, and its counter.

**`expected_wake_at` was published when it meant nothing.** It was serialised
from the row in every state, so a device that had woken, gone overdue, or been
retired from battery mode still advertised a wake instant — against
`http-api-boundaries.md` §2.3, which says it is present only while `sleeping`.
It is now read off the derived state, and only `SleepingExpected` carries one.

**An inconsistent sleep row resolved to a reachable state.** A `sleeping` row
with no window derived `Reconciling`, which reads as *present*. It derives
`isolated`, per SAFETY-012.

**`power_mode` was a one-way latch.** `CASE WHEN declared_battery` meant a device
that had once declared battery mode stayed `battery` for ever, keeping a widened
liveness cadence and remaining eligible to open sleep windows, even when it
explicitly declared `always_on`. The mode now follows any explicit declaration
and an unknown mode retires the battery state, while an *absent* `power` block
still changes nothing — that is a pre-ADR-018 payload declaring nothing rather
than declaring always-on. A Last Will no longer redeclares power configuration
at all: it is composed at connect and delivered at an arbitrary later moment, so
it is evidence of a dropped session and nothing else.

**The sleep-announcement rule existed twice.** `DeviceStatus::validate` and
`persist_status` each spelled out "offline, `sleeping`, battery, 60–86400". One
copy now lives in the contract as `announced_sleep_interval_seconds`, with
`declared_power_mode` beside it, for the reason there is one
`validate_water_command`.

**Staleness was one function answering two questions.**
`max(15 min, 3 × interval)` is SAFETY-005's `max_sample_age`, and F-040-26 was
feeding it a device-declared `wake_interval_seconds` of up to 86 400 seconds. M6
does not exist yet, so nothing was broken — but M6-005 depends on M4-004 and
would have inherited the pattern, and a device able to advertise itself a
three-day freshness window is SAFETY-021's failure arriving through the staleness
door. The calculation is now split: `max_sample_age_seconds` takes a cadence and
nothing else and is what M6-005 must call, and `liveness_interval_seconds` is the
only place the battery widening exists, bounded at 3600 seconds — the slowest
cadence `device.config` may ask for. The documented 900-second example is
unchanged at 45 minutes. Beyond the cap a battery device reads `stale` while its
connectivity honestly reads `sleeping`; the two answer different questions and
are allowed to disagree.

**Verified and found correct.** M3 remains the only MQTT consumer, decoder, and
status-order authority; the correction added no consumer and no ordering path.
Duplicate and logically old status still change no registry state and never
refresh `last_seen_at`. Every valid status receipt, duplicates included, still
publishes non-retained QoS 1 `edge.time`, because that publish sits outside the
dedup branch. The four states are `Online`, `SleepingExpected`,
`OfflineUnexpectedly`, and `Reconciling`, presented as `connected`, `sleeping`,
`isolated`, and `reconciling` in code, REST, and docs alike. `expected_wake_at`
derives only from the edge `received_at` plus the relative interval;
`expected_wake_ms` is read nowhere. Sleeping devices are excluded from
`devices_offline`, the gauges are recomputed per sweep, and no new label was
added to any metric. Migration `0006` is additive, no applied migration was
edited, and its defaults leave every pre-existing device always-on.

**Tests added.** All four `safety_021_*` tests the invariant registry names now
exist, plus `safety_021_an_incomplete_sleep_window_is_never_reachable` and
`safety_005_control_freshness_cannot_be_widened_by_a_declared_wake_interval`. A
new file-backed `restart_replay` suite closes and reopens the database to prove
that a sleep deadline survives a restart, that a retained redelivery extends
nothing, that a missed wake is counted once however many sweeps run and is not
re-counted after a restart, that a late wake recovers, that a delayed
older-generation Last Will cannot regress it, and that each sleep cycle can miss
at most once. A live-Mosquitto test restarts the broker and proves the retained
announcement replayed on re-subscribe moves neither the window nor
`last_seen_at`. `upgrading_a_populated_pre_battery_database_preserves_always_on`
applies `0001–0005`, inserts a device, then upgrades and checks the row and the
resulting schema against a fresh database.

**Negative controls.** Four mutations were applied and reverted: removing the
deadline check from the derivation failed four tests across three modules;
restoring the `power_mode` latch failed the retirement test; removing the
liveness cap failed the SAFETY-005 separation test. A fourth — removing the
redundant `AND connectivity_mode='sleeping'` guard from the missed-wake `UPDATE`
— failed nothing, because the Rust-side condition already prevents re-entry. The
SQL guard was kept as concurrency defence and the result is recorded here rather
than papered over.

**Fixtures.** The corpus had no `power` block at all, valid or invalid.
`valid/status-sleeping.json` and three fixtures under
`invalid/status_sleep_wake_interval/` (out-of-range interval, unknown mode
claiming sleep, no power block) were added with their `Expected` arm, valid
status fixtures now run `DeviceStatus::validate`, and a compatibility test
asserts every pre-ADR-018 status fixture still decodes, declares no power mode,
and does not materialise a `power` field on re-encode.

**Planning.** SAFETY-021's enforcing milestone moved from M5 to **M4** in the
registry and in ROADMAP, because the derivation and the timer are here. M4's exit
criteria gained the battery clauses and M5's lost them, keeping only what a
simulator must demonstrate. M5-020 is wholly superseded, with the two of its own
instructions the original correction did not honour recorded in it. M5-019 was
reduced to genuinely unimplemented scope — battery measurement kinds,
`device.config.power`, a typed `wake_reason`, and the config-side fixtures — with
the delivered status half listed explicitly so it cannot be built twice.
F-040-20, F-040-21, and F-040-26 were reworded to describe what the code does:
`power_mode` comes from the device's declaration until M5-019 makes it
configuration, the connectivity value is derived at read time, and the battery
staleness widening is capped and separate from SAFETY-005.

Final state remains: **M4 DONE · M5 READY · M5 not started**.
