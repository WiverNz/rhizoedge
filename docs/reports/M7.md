# M7 — Cloud Sync and Storage

**Status:** DONE — 2026-08-31. M7-001 through M7-015 and every PRD 070
acceptance criterion were demonstrated. M8 is READY and has not started.

## Delivered

The `cloud-api` Rust binary runs beside PostgreSQL 17 in Compose. Its migration
creates `edge_instances`, the append-only `synced_events` ledger, and the
`devices`, `plants`, `measurements`, `watering_events`, and `device_events`
projections. Ledger identity is `UNIQUE(edge_id,event_id)`; ingestion uses
`ON CONFLICT DO NOTHING`, so a repeated event is a successful `duplicate`.
Unknown kinds are committed unchanged to JSONB ledger history and reported as
rejected for projection. A batch and all of its projections commit in one
PostgreSQL transaction. Projection rules use natural keys and timestamp guards,
so input order cannot move current state backwards.

The only cloud write route is `POST /api/v1/edges/{edge_id}/events`. Historical
reads cover edges, devices, plants, measurements, and watering events, with
bounded cursor pagination, time ranges, and raw/minute/hour/day measurement
resolution. There is no command route, configuration write route, or polling
route. `/health/live` is process-only; `/health/ready` checks PostgreSQL.

`rhizo-cloud-client` owns typed request/result/error models, bounded requests,
exhaustive retry classification, and RFC 7231/9110-compatible `Retry-After`
parsing for both delay-seconds and IMF-fixdate. Its time conversion property
test preserves every representable millisecond exactly.

Edge uses one canonical SQLite outbox writer and assigns `measurement.sample`
to the low tier; every other ADR-005 kind is high tier by safe default. When
enabled, domain mutations and their cloud event are committed in the same
SQLite transaction and UUIDv7 `event_id` is generated once. When disabled,
there are no outbox writes and no drain task. The independently supervised drain
uses oldest-first batches, accepted/duplicate completion, permanent rejection
quarantine, unlimited full-jitter 1–300 second retry, `Retry-After`, timeout
halving to a floor of 10, and gradual recovery to 500. Cap enforcement runs even
when all rows are delayed; only oldest low-tier rows can be pruned, while high
tier rows are never deleted. Status, quarantine, and bounded-cardinality
Prometheus surfaces expose the lifecycle.

Reprojection deletes and rebuilds one edge's projections inside a single
transaction, logs progress, checks cardinality consistency, remains readable
until commit, and is safe to repeat. It never mutates the ledger.

## Post-M7 correction — 2026-08-31

A focused audit of the cloud event catalogue against
[ADR-005](../adr/005-cloud-event-model-and-idempotency.md), which is canonical
and was not amended. M7 was not reopened as a milestone — the treatment M0 got
in the 2026-08-26 pass, M4 got in the battery pass, and M6 got in the post-M6
correction — because M8 has not started. Nothing here changes the architecture,
the ADR-005 catalogue, the wire protocol, or the safety gate.

### What was wrong

**1. The edge emitted a kind the catalogue does not contain.**
ADR-005 names `device.capabilities`; the edge emitted
`device.capabilities_changed`. `cloud-api` already recognised only the ADR name,
so every capability change would have been committed to the JSONB ledger and
then **rejected for projection** and quarantined at the edge — quietly, because
a quarantined event is a row in a table, not an alert. Neither side had a test
that could see the difference: the edge asserted its own string and the cloud
asserted its own string, and the two were never compared.

**2. Destructive state changes emitted nothing at all.**
`delete_sensor_binding`, `delete_actuator_binding` and `delete_measurement_policy`
each removed a row and returned `true` without writing an outbox event. So did
`delete_offline_policy`, `plant::delete` (the soft delete), and
`materialize_preset` — which writes the same `measurement_policies` rows
`upsert_measurement_policy` writes, through a different door. Cloud history
therefore recorded configuration being **created** and never being **removed**,
which is the failure mode where a reader reconstructs a plant that has bindings
it no longer has.

**3. Three catalogue kinds had no reachable edge emitter.**
`persist_replay` committed replayed device events, `history_gaps` rows and
`watering_events` rows without touching the outbox, so `history.gap`,
`watering.offline_autonomous` and `device.policy_applied` never left the edge.
ADR-005 §Replay says in as many words that "replayed offline history is just
more events" and that forwarding it is what the idempotency key exists for; an
isolated device's autonomous doses were the one part of history the cloud could
not see.

**4. The README still said M7 had not started.**
Its status block read "M0 through M6 complete. M7 ready, and not started" while
this report said `DONE`, the ROADMAP said `M0–M7 complete`, and the code shipped.
The front page is the one document a reader meets first, and it was the last one
anybody updated. Its component table also predated the milestone: `cloud-api` was
a single clause and `rhizo-cloud-client` was absent entirely. Its project gate
listed only `RHIZO_REQUIRE_BROKER`, two required-service flags short.

**5. The evidence for M7-014 could not have caught any of it.**
`complete_catalogue_has_safe_tiers` asserted the catalogue had 25 entries and
that their tiers were right. It never asked whether the names matched the ADR,
whether anything emitted them, or whether the cloud agreed.

### What changed

| Was | Is now |
|---|---|
| `emit(tx, "some.string", …)` | `emit(tx, EventKind::SOME_KIND, …)` — a newtype whose only constructors are the 25 catalogue constants, so an undocumented kind is a **compile error** |
| The edge emitted `device.capabilities_changed` | `device.capabilities`, the ADR name. The edge's *local* `device_events.kind` is still `capabilities_changed`; that is a different vocabulary and is deliberately unchanged |
| A delete emitted nothing | The canonical kind for the thing that changed — `plant.binding_changed` or `plant.policy_changed`, `plant.updated` for a plant — with `operation: "delete"` and the prior row's identity and state, in the same transaction, only when a row actually changed |
| `materialize_preset` emitted nothing | One `plant.policy_changed` per policy row plus one `plant.updated`, in its existing transaction |
| `upsert_offline_policy` emitted nothing | `plant.policy_changed`, and **only when the version guard actually wrote a row** |
| Replayed offline history never reached the cloud | `history.gap`, `device.policy_applied`, and `watering.offline_autonomous` are emitted from the replay transaction, once per newly committed `event_id` |
| `cloud-api`'s known kinds were a `matches!` arm list | A `KNOWN_EVENT_KINDS` array, checked against the ADR by a test |
| Nothing compared the two catalogues | Both are checked against the **same fenced block in ADR-005**; the ADR is the canonical catalogue and neither side can drift from it silently |

No new event kind was invented. Every emission added uses a kind ADR-005 already
defines.

### Decisions worth knowing before touching this again

**A delete is an `operation`, not a kind.** The catalogue is closed, and a
`plant.binding_removed` invented at the edge would arrive at the cloud as an
unknown kind: ledgered, rejected for projection, quarantined. The delete payload
therefore carries the same kind as the upsert plus `operation: "delete"` and
enough of the row that went away to be worth reading later — a historical event
saying only "something was unbound from this plant" answers no question anyone
will ask of it.

**An unattributed autonomous dose is emitted by reconciliation, not by replay.**
A `watering.offline_autonomous` is projected against a plant, and a dose from a
device that predates `detail.plant_id` has no plant at replay time. Emitting it
there would produce an event the cloud cannot project. `control::reconcile`'s
fallback attribution is where the plant is actually decided, so that is where the
event is written — from the transaction that decides it, which also now commits
the per-plant rows and the `attributed` marker together instead of one statement
at a time.

**A device-side `lockout.set` stays a `device.event`.** ADR-005's `lockout.set`
is the *plant* lockout the edge sets, with a plant-shaped payload. A replayed
device lockout is a different fact; giving it the same kind would put a
device-shaped payload where the cloud expects a plant-shaped one.

**`fertilisation.applied` has no edge emitter, on purpose.** There is no
fertilisation feature in v1 — no table, no route, no ingest path — so there is
nothing truthful to emit, and inventing an emitter would be worse than saying
so. It is listed in `EventKind::WITHOUT_EDGE_EMITTER`, which the reachability
test treats as the exhaustive exception list: a kind that quietly *loses* its
emitter fails that test rather than joining a growing list of excuses. The cloud
still recognises and projects the kind, so a later milestone adds an emitter and
nothing else.

**The fallback's row decoding is checked at compile time.**
`attribute_autonomous_doses` reads its rows through `query_as!` and a typed
`UnattributedDose` rather than `Row::get`. `Row::get` panics on a renamed or
retyped column, and the moment it would do so is a device coming back from
isolation — reconciliation aborts and the doses stay unattributed, which is the
one path that must not fail. This is the first SQLx macro in `edge-controller`;
the ordinary build with `DATABASE_URL` unset reads `.sqlx/` and was verified to
still compile.

The one nullability override earns its place. SQLx reads
`watering_event_id` as nullable and it is right to: in SQLite a `TEXT PRIMARY
KEY` is **not** implicitly `NOT NULL`, so the schema really does permit a null
there. `started_at` needs no override because its `NOT NULL` is real — which is
what makes the single `!` a statement rather than noise. Adding `NOT NULL` to
`watering_events.watering_event_id` in the pre-release baseline would remove even
that, and is left for whoever next opens `migrations/edge/`.

Regenerating the cache also pruned one genuinely dead entry — an
`INSERT INTO pending_cloud_events(…) VALUES(?,?,'low','{}',…)` that no longer
exists in any source file, at this commit or at `e9a83b1`. That stale row is
exactly what the "potentially unused queries" warning quoted in M7's own gate had
been pointing at, and `cargo sqlx prepare --workspace --check` is now clean.

**A detected or replayed dose is water already delivered.** `project_watering`
treated only `watering.completed` as complete, so `watering.detected` and
`watering.offline_autonomous` would have projected as perpetually `started` with
a null `completed_at`. Corrected in the same pass.

### Known limitation, recorded rather than fixed

The cloud `plants` projection has no `deleted_at` column, so a soft delete is
visible in the ledger and in the projected `payload` (`operation: "delete"`) but
not as a column. The fact reaches the cloud and is not lost; adding the column is
a cloud schema change and belongs to whoever next opens `migrations/cloud/`.

### Regression protection

Five layers. Layers 1, 3, 4 and 5 each fail independently on the original
mismatch; layer 2 closes the one route that would get past the type.

1. **The type.** `emit` takes `EventKind`. `emit(tx, "device.capabilities_changed", …)`
   does not compile.
2. **`emit_is_the_only_production_writer_of_the_outbox_table`.** The type can
   only be bypassed by writing `pending_cloud_events` directly, so nothing else
   is allowed to.
3. **`catalogue_matches_adr_005`** (storage) and **`known_kinds_match_adr_005`**
   (cloud-api) parse the fenced block out of ADR-005 and compare it to their own
   catalogue, in order.
4. **`every_catalogue_kind_has_an_edge_emitter`.** Scans the storage and
   edge-controller sources for each constant; a kind with no emitter and no
   exemption fails.
5. **`a_capability_change_emits_the_adr_005_kind`.** Asserts the *wire string* in
   `pending_cloud_events.kind` after a real capability change across a reboot,
   and asserts the pre-correction name is absent.

Verified by mutation rather than assumed. Setting `DEVICE_CAPABILITIES` back to
`"device.capabilities_changed"` fails `catalogue_matches_adr_005`,
`every_catalogue_kind_has_an_edge_emitter`, and
`a_capability_change_emits_the_adr_005_kind`. Changing the cloud array's entry
the same way fails `known_kinds_match_adr_005`. Both mutations were reverted.

New behavioural tests: nine in `repo::binding::tests` (per-delete payload and
identity, delete-of-nothing emits nothing, repeated delete emits once, disabled
cloud writes no row, rollback leaves neither state nor event, preset emission,
refused offline-policy version emits nothing), one in `repo::plant::tests`
(soft delete emits once, never twice), three in `control::reconcile::reconcile`
(named dose emitted exactly once across a re-replay, fallback dose emitted by
reconciliation, gap/policy/lockout kind mapping), one in `api::devices::tests`,
and three near-miss/parity tests in `cloud-api`.

## Post-M7 outbox-retention correction — 2026-08-31

A second focused pass, over the three mechanisms that decide which outbox rows
survive: retention, the cap, and the order the drain applies them in. M7 was not
reopened as a milestone and M8 has not started. No architecture, protocol, or
safety-gate change.

### What was wrong

**1. F-070-29 was implemented and completely untested.**
`retention::run_batch` did delete synced rows older than 24 h, and nothing
anywhere asserted it. The one retention test checked `processed` and
`measurements` and never read `p.outbox` — so the requirement had an
implementation, a tick, and no evidence. The boundary was `synced_at < cutoff`,
which leaves a row synced *exactly* 24 h ago alive until the next pass. Reachable
in every test, because the clock is injected rather than sampled.

**2. Low-tier quarantined rows were counted as pressure but were unprunable.**
The cap measured `status!='synced'` — pending **and** quarantined — and then
deleted only `status='pending'`. Every quarantined low-tier row therefore did two
wrong things at once: it inflated the excess, evicting one extra *live* pending
row apiece, and nothing could ever remove it. An unbounded class hiding inside
the mechanism whose entire job is bounding growth.

**3. The drain selected before it pruned.**
`ready()` ran first; `prune_low` ran after. One mistake, two wrong answers:

- A row could be selected into the batch, then pruned, then counted in
  `cloud_events_dropped_total`, and then **transmitted anyway** from the stale
  batch. The counter said the history was dropped while the cloud received it,
  and the two disagreed permanently afterwards.
- `pending_cloud_events` was read *before* pruning, so the gauge reported the
  pressure that caused the prune rather than the backlog the prune left — exactly
  inverted from what an operator watching for recovery needs.

Retention was not in the drain at all. The cap was therefore measured against a
table that could be full of delivered receipts already past their deadline, and
those receipts evicted live low-tier history to make room for themselves.

**4. `M7-008`'s first acceptance criterion was not true.**
"Growth stops at the cap" cannot hold under high-tier-only pressure without
deleting the ledger, which F-070-27 forbids. The code was right and the criterion
was wrong; nothing tested the case either way.

### What changed

| Was | Is now |
|---|---|
| F-070-29 inline in `retention::run_batch` | `outbox::prune_synced`, the single implementation, called by both the retention worker and the drain |
| `synced_at < cutoff` | `synced_at <= cutoff` — "pruned after 24 h" is a deadline, not a half-open interval |
| A `synced` row with `NULL synced_at` could never age out | Deleted regardless of age; its status already says the cloud has it |
| Cap counted `status!='synced'`, deleted `status='pending'` | Counted and prunable are the same set, differing only by tier |
| `ready()` → prune → gauge | prune synced → prune cap → gauge → `ready()` |
| The ordering lived inline in the loop | Extracted as `sweep_and_select`, which is what made it testable without a cloud |
| "Growth stops at the cap" | Stated as it is: the cap yields to preservation, and the outbox may exceed `outbox_max_rows` |

`prune_synced` uses `sqlx::query!` rather than `sqlx::query`, because retention's
module contract (M3-004) is that every retention statement is checked against the
migrated schema at compile time, and delegating must not quietly drop that.

### Decisions worth knowing

**Retention and the cap answer different questions, and conflating them is the
bug.** Retention removes rows the cloud **already has**, by `synced_at` age, both
tiers alike — a delivered measurement and a delivered watering event are equally
receipts. The cap removes rows the cloud **does not have**, and only low tier,
because that is history that would otherwise be lost rather than merely
forgotten locally.

**The cap is allowed to lose.** Under high-tier-only pressure `prune_low` deletes
nothing and the backlog exceeds `outbox_max_rows`. This is recorded in PRD 070
beside F-070-27 and asserted by
`the_cap_yields_to_preservation_under_high_tier_pressure`, specifically so a
later reader who sees the cap "not working" does not fix it into a data-loss bug.
The bound that does apply to high-tier rows is delivery, not deletion.

**The ordering is asserted as a set relationship, not a call order.** The test
says no row the sweep deleted appears in the batch the sweep returned. That stays
true however the function is later rearranged, which a call-order assertion would
not.

**The shared-metric lock now works in both directions.** `api::health::gauge_lock`
documented that "anything else that asserts on a shared gauge must take this lock
too", while being private to `health::tests` and therefore unreachable from the
drain tests that *write* `pending_cloud_events` and `cloud_events_dropped`. It is
now `pub(crate)` at module scope and taken by both sides. A lock only one side
takes is not a lock — and these counters are process-global, so the drain tests
were reading deltas another test could move underneath them. Two of them did fail
that way before the lock was applied.

### Regression protection, verified by mutation

Each defect was re-introduced, the suite run, and the mutation reverted:

| Mutation | Caught by |
|---|---|
| `synced_at <= ?` → `synced_at < ?` (and the NULL arm dropped) | `synced_rows_are_retired_at_twenty_four_hours_and_not_before`, `a_synced_row_with_no_timestamp_is_not_an_unbounded_class` |
| Cap prunable set `status!='synced'` → `status='pending'` | `low_tier_quarantined_rows_are_prunable_not_permanent_pressure` |
| `ready()` moved back before the prunes | `a_row_the_sweep_drops_is_never_in_the_batch_it_returns` |
| Gauge read moved back before `prune_low` | `the_pending_gauge_reports_the_backlog_after_pruning_not_before` |

Eight new tests in `repo::outbox::tests`: the 24 h boundary in three positions;
pending and quarantined never retired at any age, including one carrying a stale
`synced_at`; both tiers retired once delivered; the NULL-timestamp orphan;
bounded oldest-first batching; quarantined low-tier prunability; the cap yielding
to high-tier pressure; and the cap ignoring delivered rows.

Four new tests in `cloud::drain::tests`: the dropped-row/batch disjointness, the
post-prune gauge, retention running before the cap is measured, and high-tier
pressure exceeding the cap while still being selected for transmission.

The drain tests build their rows through `outbox::emit` rather than raw SQL —
`emit_is_the_only_production_writer_of_the_outbox_table` caught the first draft
doing otherwise, which is the check earning its place on the day it was written.
