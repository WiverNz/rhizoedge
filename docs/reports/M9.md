## 1. What M9-001 actually found

M9-001's job was to execute ADR-007's toolchain section on a real machine and
correct it from what happened. It happened, and the ADR was wrong in four
places. [ADR-007](../adr/007-esp32-rust-framework-and-toolchain.md) now records
the corrections; this is the summary.

### The Rust-version question is resolved: outcome 2

**Stock Rust 1.98.0 cannot build `riscv32imc-esp-espidf`.**

```text
$ rustup target add riscv32imc-esp-espidf --toolchain 1.98.0-x86_64-pc-windows-msvc
error: toolchain '1.98.0-x86_64-pc-windows-msvc' has no prebuilt artifacts
       available for target 'riscv32imc-esp-espidf'
```

`rustc --print target-list` knows the triple — it is a recognised tier-3 target
— but no `std` is distributed for it, so `std` must be built from source with
`-Z build-std=std,panic_abort`, which is nightly-only. ADR-007 anticipated this
as one of two acceptable outcomes and it is the one that happened.

The firmware **image** workspace therefore pins `nightly-2026-07-01`
(rustc 1.98.0-nightly, f46ec5218) with `rust-src`. A dated nightly, not
floating: CI runs clippy with `-D warnings`, and a floating nightly turns a
green branch red with no code change.

**The exception is contained more tightly than ADR-007 required.** The host
workspace is untouched at 1.98.0, and so is `firmware/node-app` — where the
actuation gate's caller, the ledger, the budget, the policy store, and their 139
tests live. Only the crate that links ESP-IDF needs nightly.

### espup does not do what the ADR said it did

ADR-007's stated reason for using espup on a RISC-V target was that "it also
provisions the ESP-IDF C environment that `esp-idf-sys` needs, which is the
harder half". It does not. `esp-idf-sys`'s build script clones ESP-IDF itself
and installs its own toolchain, cmake, ninja, and Python virtualenv into
`<drive>/.embuild/espressif`.

### `espup install --targets esp32c3` is not sufficient, and fails late

For a RISC-V-only selection espup adds three bare-metal `riscv32*-none-elf`
targets, writes an **empty** export script, and installs no LLVM. The build then
runs all the way through cloning ESP-IDF and compiling its ~110 C components —
341 seconds — before failing:

```text
Unable to find libclang: "couldn't find any valid shared libraries matching:
['clang.dll', 'libclang.dll'], set the `LIBCLANG_PATH` environment variable"
```

The `libclang` `esp-idf-sys`'s bindgen needs ships with the LLVM espup installs
alongside the **Xtensa** toolchain. `espup install --targets all --std` is
required, even though nothing here builds for Xtensa.

### Both halves of the export script are load-bearing on Windows

It sets `LIBCLANG_PATH` to the DLL *and* prepends `esp-clang/bin` to `PATH`.
Setting only `LIBCLANG_PATH` fails with `LoadLibraryExW failed` — the DLL is
found and cannot be loaded, because its dependencies live in that directory.
Measured both ways: with the directory on `PATH` the build succeeds in 29.5 s;
without it, it fails.

### The Windows path limit is a hard stop

`esp-idf-sys` refuses an `OUT_DIR` longer than **88 characters** after
canonicalisation. The fixed suffix cargo appends is 73 characters, so
`CARGO_TARGET_DIR` must be **15 characters or fewer**. This repository's natural
target directory is 47.

```powershell
$env:CARGO_TARGET_DIR = "D:\rzt"
```

`ESP_IDF_PATH_ISSUES=warn` downgrades it to a warning and is recorded only so
nobody has to find it; it moves where the build fails rather than fixing
anything.

## 2. What was built

Two workspaces, and the split is a deliberate improvement on ADR-007's sketch.

```text
firmware/
├── node-app/       WORKSPACE A — host toolchain 1.98.0, no ESP-IDF dependency
└── esp32-node/     WORKSPACE B — nightly + build-std, riscv32imc-esp-espidf
```

ADR-007 put the host-testable layer in `firmware/esp32-node/src/app/` and
enforced "no `esp_idf_*` import" with a grep. A separate crate makes the same
property **structural** — the crate has no ESP-IDF dependency, so an ESP-IDF
symbol there does not compile — and ADR-007 explicitly permitted a cleaner
separation that achieves the same isolation. Two consequences, both wanted: the
safety logic is compiled by the host pin rather than by nightly, and
`cargo test` in `node-app` needs no target flag, no `build-std`, and no ESP-IDF
installation at all.

| Concern | Module |
|---|---|
| hardware traits and their fakes | `ports.rs`, `fakes.rs` |
| boot ordering (SAFETY-011) | `boot.rs` |
| persisted state, CRC | `persist.rs` |
| identity, boot identity | `identity.rs` |
| **the one actuation path** | `command.rs` |
| pending-result ledger | `ledger.rs` |
| dedup ring (SAFETY-001) | `dedup.rs` |
| interrupted dose (SAFETY-011) | `recovery.rs` |
| configuration (§5.7) | `config.rs` |
| policy store, atomic activation (SAFETY-019) | `policy.rs` |
| **the one offline evaluator call site** | `offline.rs` |
| monotonic budget, `credit_elapsed` (SAFETY-015) | `budget.rs` |
| event buffer, gaps (SAFETY-016, -020) | `buffer.rs` |
| power mode, wake cycle (ADR-018) | `power.rs`, `awake_hold.rs` |
| rails, warm-up | `sampling.rs` |
| telemetry, ring, status | `telemetry.rs` |
| serial provisioning | `provision.rs` |

The ESP crate holds `main.rs` (pump-off first), `run.rs` (the session loop),
`board/` (the only place a GPIO number appears), `hal/` (ESP-IDF adapters), and
`net/`.

## 5. The pending-result ledger decision (M9-011)

**Capacity 16. No eviction. Actuation refused at 15, with
`RejectReason::ResultLedgerFull`.**

Recorded against ADR-014's six points in
[ADR-014](../adr/014-failure-and-retry-policy.md) §Device-side pending-result
ledger and in [PRD 090](../prd/090-esp32-rust-firmware.md) Open question 5, both
now resolved. In brief:

1. **New actuation is refused while saturated.** The check is a device-local
   veto that runs **after** `validate_water_command` has already accepted — the
   same shape M16's delivery witness will take — so the shared gate stays the
   only gate and this can only ever stop a dose.
2. **Already-delivered water stays attributable.** Nothing is evicted, and
   `delivered_today_ml` rides on every result and in `device.status` as an
   independent running total.
3. **Saturation is visible** as a durable fault, latched once per episode and
   cleared on the crossing back, reported with the volume the edge has not yet
   counted.
4. **Recovery is per `command_id`**; an unknown acknowledgement is a no-op.
5. **Reboot at the boundary is safe** — the ledger is persisted before the
   publish, into the inactive of two CRC-protected NVS slots.
6. **No eviction is adopted**, and no safety-equivalence argument is offered,
   because there is not one to make.

**Why a new refusal reason rather than reusing one.** `pump_unavailable` was the
cheap option and it would have told the edge something false: the pump is fine.
An operator chasing a pump fault that does not exist is worse served than one
told the ledger is full. `RejectReason::ResultLedgerFull` was added additively
to the shared contract; both ends already decode an unrecognised reason to
`unknown`, so a device or an edge that predates it still interoperates.

**Why the reserved slot.** A refusal is *itself* a `command.result` and needs
somewhere to live. Without the reserve the device could reach a state where it
cannot record the refusal it just issued. If the ledger is nonetheless
completely full, a **rejection** is published once, un-ledgered and unretried —
sound for that one class of result and no other, because a rejection reports
zero delivered water and losing it cannot under-count anything.

**Why 16.** It matches `COMMAND_DEDUP_RING`. A deeper ledger could hold a result
for a command the ring had already forgotten.

## 6. Deviations and findings

**Two workspaces, not `src/app/`.** ADR-007's illustrative layout is not what
was built; the isolation it exists for is stronger. ADR-007 permitted this
explicitly and has been updated to describe the layout as built.

**The structural tests live in `node-app/tests/`, not `esp32-node/tests/`.**
M9-003 asks for a structural board-isolation test "run as an ordinary test in
the firmware workspace". `esp32-node` builds for the ESP target, so `cargo test`
there would cross-compile a binary that cannot run without a board. The checks
are on source text and need no target, so they run in the workspace that can
execute them — with no board, no ESP-IDF, and no nightly. They scan
`../esp32-node/src` and assert they found files first, so a moved crate fails
loudly rather than passing vacuously.

**`credit_window` had a real hang.** Written as a subtract-in-a-loop, a credit
of `u64::MAX` — which a corrupted RTC word can present — is about 2×10¹¹
iterations against a day-long window. On an ESP32 that is a watchdog reset
inside the accounting code, which is the last place to hang. Found by a host
test taking 60 seconds; fixed with `%`. This is precisely the class of bug the
host-testable split exists to catch.

**The conformance suite found a wire divergence on its first run** —
`delivered_ml: Some(0.0)` versus `null` on a rejection. See §3.

**The first CI run reached the M8 scenario suite for the first time ever, and
found a latent race in it.** Every previous `End-to-end` run had died in setup
after ~25 s (`gen-dev-env.sh: Permission denied`, fixed by the preceding
commit), so no scenario had ever executed on a runner. This one got there and
`scenario_normal_telemetry` failed with `telemetry counts are inconsistent:
(66, 11, 11)` — eleven batches where the assertion demanded exactly ten.

The scenario read `count(DISTINCT batch_id)`, saw ten, then stopped the
simulator and re-read. Stopping a container is not instantaneous and a batch
already on the broker is still delivered afterwards, so an eleventh batch landed
between the two reads. **The assertion was unprovable as written**: nothing can
stop a publisher at an exact count.

Fixed by asserting the property rather than the number — the batch count must
*reach* ten, and then, on a snapshot taken once ingestion has settled, every
batch must carry exactly one `received_at`, no two batches may share one, every
batch must have stored at least one sample, and `received_at` must never
regress. Batch atomicity is what protocol §3 actually promises, and it is true
of eleven batches exactly as it is of ten. The observation that failed CI —
`(66, 11, 11)` — satisfies every one of the new assertions.

Fixing that exposed a **second** latent flake immediately behind it.
`scenario_rolling_cap_across_midnight` spends the daily cap, waits for the next
virtual midnight, and asserts a further dose is still refused. But the cap is a
**rolling 24-hour window derived from rows** (SAFETY-006), not a calendar day —
so the assertion is only meaningful while the doses are still *inside* that
window, and whether they are depends on where in the virtual day the scenario
happens to start.

The diagnostics settled it with numbers rather than argument. The five doses
were issued from virtual 1788392784012; the sixth, which was accepted, at
1788480316815 — **24.315 virtual hours** after the first. The window had
genuinely elapsed and released 60 ml. **The edge was right and the invariant
held**; the scenario asserted something false. It had always been one virtual
hour from failing, and the settle loop added to `normal_telemetry` shifted the
clock just far enough to tip it.

Fixed by approaching the boundary deliberately: wait until midnight is within
two virtual hours, *then* spend the cap, *then* cross. The doses are a couple of
virtual hours old when the check runs, which is the situation the invariant is
about, and the premise is now asserted explicitly so a future drift reports
"this scenario is testing nothing" instead of passing vacuously.

Both are M8 code, not M9, and are recorded here because M9's commit is what
exposed them. PRD 080 is explicit that a flaky scenario is fixed and never
retried to green.

**The e2e job's budgets had never been measured either, and getting them right
took two attempts.** With both scenarios fixed the suite ran clean and the *job*
was killed at 15 minutes: setup — checkout, buildx, the bake build, image
extraction — took **14m16s**, leaving 57 seconds in which 14 of the 41 scenarios
ran. The budget had been set when the job had never reached a scenario, so it
had never had to fit one.

Raising it to 30 minutes with a 10-minute budget on the suite step was the
right *shape* — a hung suite and a slow build should fail differently — but the
step number was extrapolated from those first 14 scenarios, which are the fast
ones. **The suite is not uniform.** Measured on a runner: median 3 s,
`scenario_long_isolation` 50 s, `scenario_offline_budget` 73 s, and
`scenario_history_gap` several minutes because it has to fill a 256-entry
telemetry buffer at the simulator's cadence. Thirty-three scenarios took 272 s
and the thirty-fourth was still running when the step budget expired.

**The underlying defect was a budget in the wrong unit.** `wait_simulator` takes
an *iteration count*, and each iteration costs an HTTP round trip whose latency
belongs to the machine — so `history_gap`'s 8 000 attempts meant about a minute
on a developer's desktop and about five and a half on a two-core runner sharing
itself with six containers. It sat within seconds of its own limit, which is the
worst place for a limit to be. It now waits against a **wall-clock deadline**
(`wait_simulator_until`, 10 minutes), so the budget means the same thing
everywhere and the failure carries the last observed simulator state.

Final budgets, from measurement rather than extrapolation: the full suite takes
**648 s for all 41 scenarios** on a fast developer machine and a runner is
roughly 1.5–2× slower again, so the suite step is 30 minutes and the job 50.

**With a budget long enough to reach it, `scenario_history_gap` then failed
properly — and said why.** The wall-clock helper printed the last observed
simulator state, and it was conclusive:

```text
buffered_events: 257, buffered_cycles: 0,
connected: true, isolation_remaining_ms: 0
```

The predicate needs `buffered_cycles >= 16` *and* `buffered_events >= 257`. The
overlay runs at `--time-scale 3600` with `--telemetry-interval 300`, so a
telemetry cycle is 83 ms of real time and the fault's 259 200 virtual seconds
were **72 real seconds** of isolation. Filling the buffer takes 257 cycles —
about 21 real seconds when the simulator keeps its cadence, and several times
that on a runner sharing two cores with six containers. **The scenario was a
race**: win it and the predicate holds while isolated; lose it and the isolation
expires, the device reconnects, the telemetry ring flushes to zero, and
`buffered_cycles >= 16` can never be true again.

The isolation duration is only a *ceiling* — the fault is disabled the moment
the predicate holds — so it is now set to 3 240 000 virtual seconds (900 real),
beyond the 600-second wait budget. The budget is therefore always the binding
limit, and a genuine problem is reported as a diagnostic instead of as a silent
reconnection.

**An unbounded wait in the untested tail was bounded at the same time.**
`scenario_sleep_budget_cooldown` spun on a bare `loop` until the cooldown
opened, with no budget and no message. Scenarios 35–41 have still never run on a
runner — the suite exits on first failure — so that loop had never been
exercised there. It now uses the same bounded wait as everything else and
reports the last observed state.

**And behind that, a real edge defect — not a test problem.**
`scenario_battery_awake_cycle` then failed locally about one run in two. The
diagnostics were unambiguous: `command_intents: 1 row`, `commands: 0 rows`, and
the edge's own log said

```text
a held dose was refused at delivery; nothing published   reason: "uncertain"
```

`uncertain` is the **reconciliation hold** — a plant is held until the replay
for the device's current boot commits a contiguous prefix (SAFETY-016). A
battery device reconnects on *every wake*, so for it that hold is a routine
momentary state rather than a verdict. Treating it as terminal meant an
operator's dose request was silently consumed whenever the mint happened to race
that wake's replay.

`control::intents` already drew exactly this distinction and applied it to one
reason: `clock_unsynced` returns `Retryable` because "the window itself is
bounded", and its final arm says of cooldowns and absorption waits that they are
"not a refusal of the operator's request, so the intent waits". `uncertain`
belongs in that set and was not in it. It is now, with the same reasoning and
the same two guarantees of termination — the hold clears when replay commits,
and the intent expires on its own clock regardless (ADR-018 §3).

**This loosens nothing at the gate.** The full gate re-runs on every delivery
attempt against inputs read *now*, and a dose is published only when it accepts;
a leak, a low tank, and the daily cap all stay terminal. What changed is only
that a transient "the edge does not know yet" no longer throws the request away.
`scenario_battery_awake_cycle` passed 3/3 afterwards, having been roughly 1-in-2
before.

**A fifth: `captured_replay_batches` read a snapshot, not a barrier.** Both its
callers waited for the *device* to report `connected` and then read the MQTT
capture immediately — but a device publishes its replay **after** connecting,
and the harness fills the capture asynchronously. On a fast machine the batches
happened to be there; on a runner they were not, and
`scenario_duplicate_replay` failed with "no replay batches were captured". It
now waits for protocol §5.4's own end-of-replay marker (`complete: true`), which
is both the correct barrier and the one that also serves the caller needing
*several* batches without guessing how long the rest take.

### Reproducing the runner locally, and the emulation that lied

Five flakes fixed one at a time, each costing a ~30-minute CI round trip,
because **this machine has 32 cores and a GitHub runner has 2** — a 16× gap that
hides every timing assumption in the suite.

The first attempt at emulating that was wrong in an instructive way: loading 30
cores with busy loops reproduces *throughput* starvation but not *concurrency
shape*. `nproc` inside the containers still reported 32, so their runtimes were
still sized for 32 while getting two cores' worth of work done — oversubscription
a runner never experiences. It duly invented a failure
(`scenario_sleeping_manual_water`, "held battery intent produced no watering
event") which the edge log immediately contradicted: the intent *was* delivered
and the command *was* minted. The shortfall was the simulator not being
scheduled, not a defect.

The faithful emulation pins the containers instead, so `nproc` inside them
reports 2:

```yaml
# scratch overlay, not committed
services:
  edge-controller: { cpuset: "0,1" }
  device-simulator: { cpuset: "0,1" }
  # ... and every other service
```

Under that — the runner's actual shape — the full suite passes **41/41 in
570 s**. That is the number the 30-minute step budget should be read against,
and it is measured rather than extrapolated.

## 7a. Corrections applied after the first pass

Three defects found by a full review of the implementation, each fixed with the
test that would have caught it.

### The image never called the offline evaluator

`offline::evaluate_and_act` had exactly one caller — its own unit test. The
loop in `main.rs` answered an unreachable router by backing off and retrying,
and `serve` returns immediately when the session is not up, so an isolated
device sampled nothing and decided nothing. Six hundred lines of host-tested
autonomy were unreachable from the binary, and ADR-015's central promise was
not delivered by anything that ships.

This was graded **DONE (host)** alongside genuinely hardware-blocked items,
which is what hid it: the missing piece needed no board. M9-006 and M9-010 are
graded **PARTIAL** for the same class of gap and were the right precedent.

`run::serve_isolated` now spends every backoff — Wi-Fi and broker alike —
sampling on the telemetry cadence and evaluating each fresh batch, and
`IsolationDriver` (`node-app`) holds the bookkeeping that has to survive between
evaluations. `safety_013_an_isolated_device_with_a_valid_policy_waters_through_
the_driver` drives the driver exactly as the loop does and asserts the pump
runs.

### The rolling budget window was implemented twice, and the two disagreed

`OfflineRuntime::credit_window` (firmware) carried the overshoot of a credit
longer than one window; the simulator's `roll_window` discarded it. After a
thirty-hour sleep against a twenty-four-hour window the firmware replenished
eighteen hours later and the simulator twenty-four — **the firmware being the
more permissive of the two**, against the implementation this project treats as
canonical. Neither was covered by the conformance suite, which reached the
command gate and stopped.

The arithmetic moved to `rhizo_policy::BudgetWindow`, which both now call, and
`conformance_budget_window_credits_identically` drives the two persisted state
shapes through one credit sequence. Restoring the old simulator semantics fails
it at the thirty-hour step.

### The simulator counted every offline cooldown down twice

`OfflineRuntime::advance` decremented `cooldown_remaining_ms`, and
`next_offline_state` decremented it again from the same `elapsed` later in the
same tick. An isolated plant became eligible for its next cycle in **half** the
configured cooldown. The firmware never had this bug, because its window
accounting never touched the cooldown.

One owner per quantity: the evaluator owns the cooldown and the confirmation,
`BudgetWindow` owns the budget, and a device owns neither. A consequence worth
knowing: the offline cooldown is now dormant while the device is connected,
which is correct — the edge is pacing the plant from rows then — and
conservative, since the first offline cooldown resumes where it left off.

## 14. Edge leak-latch correction (2026-10-21, board-free)

Not M9 scope by issue, recorded here because M9 is the open milestone and the
defect surfaced on its CI. No firmware, wire, or `no_std` crate changed.

### The defect

End-to-end run 39663877363 (commit `b7771b6`, a toolchain-only change) failed
`scenario_leak` with `409 wrong_reason: uncertain`. The edge log showed the
cause: at `time_scale = 3600` the 900 s leak freshness is about 250 ms of real
time; the latched `leak` reading aged out between ticks, `safety_gate` answered
step 2 (`LeakState::Unknown → Uncertain`) **before** step 3 (a sticky lockout
outlives its condition), `control::irrigation` persisted `uncertain` over
`leak`, and the next tick with fresh readings auto-cleared `uncertain`. A leak
lockout was lifted with no operator — against SAFETY-003 and F-060-41. The
scenario's fixed 600 ms sleep made the window reachable; the gate made it
unsafe. The existing `clearing_a_leak_lockout_needs_the_signal_positively_absent`
advanced the clock but never ran a tick, so it could not see it.

### The fix

`safety_gate` order is now: step 0 actuator, step 1 `Detected → Leak`, step 3
sticky-or-held lockout, step 2 `Unknown → Uncertain`, then the rest unchanged.
Every early return refuses, so the reorder cannot create a permission — it only
changes which reason is reported, and the reported reason is what the edge
persists and what `is_auto_clearable` judges. The lockout-clear API is
unchanged and still demands a positively clear signal.

`scenario_leak` no longer sleeps. `clear_leak_on_fresh_dry_reading` waits for
leak rows newer than the last wet one, asserts on every poll that the lockout is
still `leak`, attempts the reset only on a dry reading newer than the first dry
one seen, and treats exactly one refusal — `leak_signal: not_clear`, a reading
that aged out in flight — as "wait for a newer reading". Any other answer, or
60 s without success, fails with the rows it saw.

### Regression tests

- `gate::leak::safety_003_an_unknown_signal_does_not_displace_a_sticky_lockout`
  — every explicit-clear reason, every mode.
- `gate::leak::safety_003_a_leak_lockout_survives_a_silent_sensor_and_its_return`
  — the tick loop folded (restated in stage 2 for the per-reason inputs).
- `gate::leak::detected_outranks_a_sticky_lockout`,
  `unknown_without_a_sticky_lockout_is_uncertain`,
  `after_a_reset_every_other_check_still_applies`.
- edge-controller `safety_003_a_leak_lockout_survives_a_silent_sensor_and_its_return`
  — real ticks: silent sensor, healthy return, no auto-clear, operator reset,
  normal operation. Failed on the old order with `left: Some("uncertain")`.
- edge-controller `safety_003_removing_the_pump_does_not_rewrite_a_leak_lockout`
  — see below. Mutation-checked: deleting the control pass's
  `actuator.is_none()` guard fails it with `no_actuator`.

`metrics::the_lockout_gauge_reflects_actual_lockouts` now takes
`gauge_lock()`, because a second unit test runs the control pass and
`plants_locked_out` is process-wide.

### Step 0 (`NoActuator`): not reachable, by caller guards only

The gate's step 0 still precedes step 3, so the *gate* would answer
`no_actuator` for a latched plant whose pump binding was removed, and
`no_actuator` is auto-clearable. It is not persisted today because both callers
of `run_pass` refuse first: `tick::irrigation_pass` skips a plant with no
actuator (SAFETY-018) and `POST /water` answers 422 `no_actuator_bound`. The new
test pins that through delete → pass → re-bind → pass. Moving step 0 below step
3 would also close it structurally, but step 0's position is SAFETY-018's
"no actuation path" rule and was left for a decision rather than changed here.

### Open: two more ways a latch can be replaced

Both found while tracing every `set_lockout` writer; neither is fixed.

1. **Forward clock step (F-060-51).** `control::clock_step_response` writes a
   held `uncertain` over **every** plant, unconditionally. Reproduced with a
   throwaway test: `leak` → forward step of 1 h → `uncertain` (held) → hold
   expires, readings healthy → `None`. The leak latch is lost without an
   operator. Skipping latched plants is *not* a pure tightening: an operator
   who resets the leak inside the cooldown would then get a plant the clock
   step should still be holding. A correct fix keeps both facts, which the
   single `lockout_reason` column cannot — an architectural decision.
2. **A detected leak replaces another explicit-clear reason.** Step 1 still
   outranks step 3 (deliberately: a leak is the most urgent thing to show), so
   `pump_fault`, `no_delivery_detected`, or `max_doses_reached` is overwritten
   by `leak`, and the operator's leak reset then lifts a fault nobody reset.
   Same single-column limitation; same decision.

## 15. Independent lockout records — stage 1, storage foundation (2026-10-21)

Board-free, edge-only. **Not effective yet**: the gate, the control loop, and
the API still decide from `plants.lockout_reason`, so the §14 open paths (clock
step over a latch, a detected leak over another latch, a `clock_unsynced`
settle over a latch, the auto-clear race, the issue race) are all still open.
SAFETY-003 is not closed.

### What landed

- `migrations/edge/0002_plant_lockouts.sql` — the first forward migration. One
  row per `(plant_id, reason)`, `kind` `latch` or `hold`, `CHECK`ed so a hold
  always has a deadline and a latch never does.
- `rhizo_storage::repo::lockout` — `latch` (insert once, original `since` kept),
  `hold` (insert or lengthen, never shorten), `clear_latch` (exactly one named
  latch; never a hold), `active` (latches plus unexpired holds, live plants
  only). Each changes its row and writes its `plant_events` row and outbox row
  in one transaction, and only when something changed. `latch` refuses a hold or
  derived reason and `hold` refuses anything but `uncertain`/`clock_unsynced`, so
  a latch can never be stored as something that expires.

### Migration safety

Fail-closed backfill from the single column: every explicit-clear reason, every
**unrecognised** reason, and a blank one (renamed `unknown`) become latches; a
known non-latch reason with a deadline becomes a hold, expired or not (the SQL
cannot see the edge clock, so the reader decides); a known derived reason with
no deadline is dropped, because the next pass re-derives it from live inputs. A
missing `since` falls back to the plant's creation time rather than losing the
row; soft-deleted plants are migrated too. Each migrated row is announced as a
`plant_events` `lockout_migrated` row (`warning` for an unrecognised reason),
and an unrecognised reason is cleared by its exact stored name — the
diagnosable way out. The backfill is `ON CONFLICT DO NOTHING` throughout, so
re-running it changes nothing and never overwrites a later record. The upgrade
is preceded by the existing automatic backup. `plants` is not modified.

### Cutover strategy

`repo::command::set_lockout_in_tx` is the **only** writer of
`plants.lockout_reason` (checked by search). From this stage it mirrors every
write into `plant_lockouts` inside the same transaction, emitting no event of
its own (the legacy writer already does): a latch or unknown reason is latched,
a held reason is held, a derived reason is skipped, and only an *operator*
clear removes a latch — the one the column named. Migration plus mirror make the
table a superset of the column from the first write after `0002`, and it keeps
the latches the column loses to an overwrite. No second import is needed at
cutover.

Order matters, and it is why stages 2 and 3 of the plan must land as one change
for the edge (the domain half can be reviewed first):

- switching **writers** before readers would stop the column receiving alarms
  the decision path still reads from it;
- switching **readers** before the operator-clear path would leave a latch the
  column had lost — now visible in the table — with no endpoint able to clear
  it.

So the decision path (`inputs::gather`, the gate), the writers (pass, clock
step, settle), and the clear endpoint's storage call move together; the API
response shape (`lockouts[]`, retiring `wrong_reason`) can follow separately.
After the switch the mirror is removed and the column is written only as a
display summary.

### Tests

`repo::lockout`: 11 — independence and single-reason clear, original `since`,
hold only lengthens and expires without touching latches, wrong-kind refusal,
unknown reason cleared by name, live plants only, file-backed restart, and four
transition tests through the legacy writer (each §14 overwrite replayed; an
operator clear removes only the named latch; the mirror records no event; the
table covers the column after every step of a mixed script). `migrate`: a real
`0001` database with fourteen legacy shapes upgraded, reopened, and migrated

### Stage 2 — the domain model (2026-10-21)

`IrrigationInputs` takes `latched: &[LockoutReason]` and `holds: &[Hold]`
instead of one `active_lockout` and one `lockout_held_until`. `lockout_class`
(exhaustive: latch, hold, derived) and `display_rank` (a fixed total order:
latches, then holds, then derived) are new in `irrigation::types`. Gate step 3
now refuses on **any** latch and **any** hold whose deadline is ahead, and
shows the best-ranked one, so the answer cannot depend on how many records
there are or the order they arrived in; step 1 (`Detected → Leak`) still comes
first and step 2 (the derived `Uncertain` of a silent leak sensor) still comes
after. A `Hold` is a type of its own, so the derived `Uncertain` and a recorded
clock-step hold cannot be confused.

**The edge's behaviour is unchanged.** `control::inputs::legacy_records`
converts the single column into the new inputs exactly as the old step 3 read
it, pinned by `the_converter_reproduces_the_old_single_lockout_rule` over every
reason and every deadline position; `lockout/clear`'s trial evaluation empties
both inputs, as it emptied the single one. Tests: `gate::recorded` (eight cases
plus a property test that the answer is identical under any reordering and
refuses exactly when a leak is detected or unknown or any latch or unexpired
hold exists), the existing gate and machine tests restated for the new inputs,
and the class/rank agreement in `types`.

### Stage 3 — the edge cut over (2026-10-21)

Readers, writers, and the clear endpoint moved together, for the reasons given
under *Cutover strategy*:

- **Reads.** `control::inputs::records` reads `repo::lockout::active` and is the
  only source of the gate's latched and held inputs; `plant::analyse` takes the
  recommendation's blocking reason from it too. An unrecognised stored name is
  `Unknown` (a latch), and a deadline too large to represent never ends.
- **Pass.** A `Lock` whose reason is latch-class and not already recorded is
  latched *beside* the existing records; nothing else is recorded. The
  automatic clear is gone: there is nothing left for a stale read to wipe
  (path E).
- **Clock step and settle.** `hold(uncertain)` and, inside the settling
  transaction, `hold(clock_unsynced)` (paths A and D). `SettleLockout` became
  `SettleHold`.
- **`lockout/clear`.** One named latch, via `clear_latch`, in a `BEGIN
  IMMEDIATE` transaction that re-reads the leak stream before deleting; a hold
  answers 409 `hold_not_clearable`; the response shape is unchanged.
- **Summary.** `command::set_summary` writes `plants.lockout_reason` for
  display only, and records `lockout_set` / `lockout_cleared` just for what no
  record covers (a derived block, a hold that expired), so each block is
  counted once. `set_lockout` and the stage-1 mirror are removed.

### What path F still leaves open

The check before an attempt commits, and only then is the message handed to
the MQTT client. A lockout recorded in that interval — or after the broker has
the message — does not stop it, and nothing recalls a published command;
`a_latch_after_authorisation_is_the_window_that_remains` states this as a test.
The client may also retransmit an accepted QoS 1 message after a reconnect.
What bounds it: the command's TTL (the device refuses an expired command), the
device's own leak and tank refusal (protocol §5.8), and the next decision, which
refuses at once. Path F is **narrowed, not closed**, and SAFETY-003 is not
declared closed. Tare and calibrate name no plant, so no plant lockout refuses
them; calibration is a real dose, and whether a plant lockout on the bound pump
should refuse it is an open question.

#### SAFETY-003: where each loss path stands

| Path | What it was | Status | Why |
|---|---|---|---|
| A | forward clock step wrote `uncertain` over a latch | **closed** | a hold is a separate row; its expiry deletes nothing |
| B | a detected leak overwrote another latch | **closed** | one row per reason; the leak reset deletes one row |
| C | `Unknown → Uncertain` answered before the latch | **closed** | gate step 3 before step 2 (§14), and the latch is a row the gate always reads |
| D | `clock_unsynced` settle wrote over a latch | **closed** | a hold row inside the settling transaction |
| E | the automatic clear removed a reason raised in between | **closed** | there is no automatic clear; derived conditions are never stored |
| F | a lockout recorded while a command is on its way out | **narrowed** | refused at issue and before every publish attempt, under `BEGIN IMMEDIATE`; not after the broker has the message |

**Ways water can still move while a plant lockout is recorded**, most serious
first:

1. **Path F's window** (narrow). A lockout recorded between
   `authorize_publish` committing and the broker taking the message, or an
   accepted QoS 1 message retransmitted after a reconnect, still reaches the
   device. Bounded by the 120 s command TTL, by the device's own leak and tank
   refusal (protocol §5.8), and by the next decision. For a **leak** the device
   refuses on its own reading if it has one; for `no_delivery_detected`,
   `pump_fault`, or `max_doses_reached` nothing on the device knows. One dose at
   most, of the size already authorised.
2. **An isolated device waters from its own offline policy** (ADR-015) and does
   not know edge latches. Pre-existing by design: the policy carries its own
   leak/tank requirements and SAFETY-013/014/017 limits, but an edge-side
   `no_delivery_detected` does not suspend it. Not changed here.
3. **`POST /devices/{id}/commands/calibrate`** runs the pump through the
   device's full §5.8 gate (leak, tank, hard limits) but no plant lockout.
   Operator-initiated and bounded, but it is a real dose while, for example,
   `pump_fault` or `no_delivery_detected` is recorded. Open question; behaviour
   unchanged pending a decision.
4. **No edge writer raises `pump_fault`.** The latch exists, migrates, displays,
   and clears, but the device's `pump_unavailable` refusal is not latched by the
   edge. A gap in detection, not a loss path; pre-existing.

**Verdict.** The independent-lockout refactor is complete for the edge: no
recorded lockout can be lost or lifted by anything but its own end condition,
across restarts and in every interleaving the tests reach. SAFETY-003 remains
**enforced, not declared closed**, because of item 1, and because the device
half still awaits a real leak sensor (M11).

**Why the stall is the environment and not this change.** The simulator's
`runner::advance` holds the device mutex while it applies the elapsed virtual
time in 60 s steps (`MAX_VIRTUAL_STEP_MS`); at `--time-scale 3600` that is about
six steps per 100 ms tick. While isolated, nearly every step changes persisted
state (a refused autonomous dose, a buffer eviction, a gap), and
`StateStore::mutate` ends in `sync_all()`. At about 16 ms per fsync — measured
on the WSL2 volume during the stall — a tick takes longer than the time it
covers, the next tick has more steps, and the mutex is never free, so
`/sim/state` and the health check stop answering. The scenario's waits are in
poll iterations, the wrong unit. Nothing in the simulator, its scenario, or
any battery path changed in stages 1–6. Recorded, not fixed: a simulator
throughput issue in test infrastructure, outside this change's scope.
