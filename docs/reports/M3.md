# M3 milestone report — Edge Ingestion and SQLite

Completed 2026-08-28. All eighteen M3 issues are implemented and verified. M4 remains READY and was not started.

## Runtime and MQTT ingestion

`edge-controller` owns named MQTT, persistence-pipeline, retention, metrics, and shutdown tasks. A panic or unexpected task exit fails the supervisor; shutdown stops ingress and drains workers to a bounded transaction boundary.

The Edge subscribes at QoS 1 to exactly:

```text
rhizo/v1/devices/+/status
rhizo/v1/devices/+/telemetry
rhizo/v1/devices/+/actuator
rhizo/v1/devices/+/commands/result
rhizo/v1/devices/+/events
```

All five subscriptions are requested after every CONNACK. The bounded ingress channel applies backpressure. The real-broker suite proves ingestion resumes after a Mosquitto restart.

The shared MQTT contract performs envelope, version, kind, and topic/payload identity validation. The injected Edge `Clock` supplies authoritative `received_at`; device time is retained only as advisory metadata.

## SQLite and transactions

Migration `0001_initial.sql` establishes the ADR-004 tables plus M3 transport tables for actuator states, command results, and replay progress. Post-M3 correction `0002_late_replay_effect_identity.sql` adds stable per-sample telemetry effect identity. SQLite runs in WAL mode with foreign keys, NORMAL synchronous mode, a 5-second busy timeout, and a four-connection bound. Required measurement, time, batch, dedup, and replay indexes are present. SQLx offline metadata is checked by CI.

Every message is processed in one transaction: insert the unique message marker, write all accepted effects and outbox state, then commit. A duplicate rolls back and is a normal no-op. Deterministic rollback tests prove there is no durable marker without its effects. SQLite busy failures use three bounded full-jitter retries before failing the message unprocessed.

## Typed telemetry and replay

Each `telemetry.batch` creates narrow typed sample rows. Shared contract validation nulls only an invalid sample's value, retains valid siblings, and records `sensor_invalid`. Unknown forward-compatible kinds remain advisory data. Actuator state remains in its own table.

Replay preserves `event_id`, `boot_id`, `device_seq`, occurrence metadata, and Edge receipt time. Event and message identities both deduplicate. History gaps are durable first-class rows. The cumulative non-retained `event.ack` is published only after commit and advances only through the highest contiguous committed sequence. A lost ACK therefore causes safe replay rather than duplicate history.

## Quarantine, retention, and observability

Malformed messages are stored with topic, bounded diagnostic error, and at most the first 1 KiB of payload. Storage is capped at 1,000 rows and admission is limited to 10 rows per device per minute; decode counters still count suppressed entries.

Retention deletes processed-message markers after 7 days. Every durable effect carries an independent stable identity, including the bounded status high-water projection described below, so no marker has to be kept to hold a logical effect down. Synced outbox rows are deleted after 24 hours, measurements after 90 days, and excess quarantine rows in bounded batches. Commands, watering events, device events, and history gaps are never pruned by M3.

### Post-M3 dedup-retention correction

The pre-M4 audit found that telemetry depended solely on the seven-day transport marker, while actuator and command-result uniqueness surfaced a late duplicate as a constraint error. Telemetry rows now use `(device_id, batch_id, sample_index)` uniqueness so a resealed batch remains one sampling effect; command results use stable `command_id`; actuator paths detect existing `message_id` effects before touching device state; replay detects stable `event_id` sets. A follow-up status audit confirmed that legitimate heartbeats use fresh message ids, so status now uses a bounded per-device `(boot_generation, sequence, current-LWT-id)` high-water projection and all transport markers are prunable. Regression tests remove markers and exercise exact and application-level replays, asserting one logical effect and unchanged current-device timestamps.

Ingestion metrics use constants from `rhizo-telemetry` and bounded labels for message kind, outcome, validation class, task, and gap tier. A cardinality guard keeps the registered series below 100 and rejects device identity labels.

### Post-M3 failure-classification correction

A second pre-M4 audit found that `Classify` was implemented on every error type but called from no runtime site: `EdgeError` was constructed only in its own tests, and the pipeline's retry helper matched `StorageError::Busy` directly. The consequence was a real inversion of [ADR-014](../adr/014-failure-and-retry-policy.md)'s table — a `Permanent` storage failure, which the ADR says must be quarantined and surfaced, instead propagated as a string to the supervisor and exited the process, so one unusable message would have stopped ingestion for every device behind it.

The pipeline now has exactly one message failure site, `apply_classification`, and the classification decides the outcome: `Fatal` propagates and the process exits, `Permanent` quarantines the message through the existing rate limiter and continues, and a `Transient` failure that has exhausted its bounded retries leaves the message unprocessed. A storage failure raised *while* quarantining is classified on its own terms, so a full or broken database still stops the process. `retry_transient` asks `classify().is_retryable()` rather than naming a variant, which is what makes a newly added error variant a compile-time decision at the point it is defined. Its backoff cap was 200 ms and is now ADR-014's documented 500 ms; the base and attempt count were already correct. The event-ack publish path, previously fatal on any `rumqttc` error, is now `EdgeError::Mqtt` and therefore transient — protocol §5.13 makes an acknowledgement advisory and does not require the edge to retry it.

`storage_bytes` was registered but never sampled, so the gauge ADR-004 and [failure-model.md](../architecture/failure-model.md) §3.6 name as the disk-fill signal always read zero. It is now sampled every 60 seconds in the retention task from SQLite's own `page_count` × `page_size`, reporting the main database and not an uncheckpointed WAL.

Tests: `pipeline::classify` asserts each of the three outcomes and that only transient failures are retried, with one attempt plus three retries; `error::classify::storage_defers_to_the_storage_classification` closes a gap where the `EdgeError::Storage` variant had no test of its own; `storage_bytes_reports_a_real_size_that_grows` asserts the gauge is non-zero and moves with the data.

## Deviations from plan

The accepted ADR schema requires a plant identifier on watering rows, while M3 can receive autonomous watering history before M5 plant binding exists. M3 therefore permits a null `plant_id` only for transported offline history; no binding or irrigation decision is inferred. M5/M6 retain ownership of interpretation.

## Known gaps carried forward

Three findings from the same audit are recorded rather than fixed, because each is a decision rather than a slip.

**The `.sqlx` offline cache covers one query.** There is a single `sqlx::query!` in the workspace, `SELECT count(*) FROM devices`, against 81 runtime-checked `sqlx::query(...)` calls. M3-004's non-goals say plainly that replacing `query!` with the runtime form "would discard the benefit", and that is what the implementation does, so `cargo sqlx prepare --check` currently proves almost nothing: a column renamed in a later migration would compile and fail at runtime. Converting the repositories is a genuine refactor — the ingestion writes are dense single-line statements with `.bind()` chains, and `query_as!` does not map onto them one for one — and it should be done as its own change with its own issue, not folded into a correction.

**The edge acknowledges QoS 1 before it commits.** `set_manual_acks` is never called, so `rumqttc` sends PUBACK during the poll that yields the publish, well before the pipeline's transaction commits. M3-005's implementation note justifies the bounded channel by saying "the broker will redeliver QoS 1 messages"; with auto-ack and the normative `clean_session = true` ([ADR-002](../adr/002-mqtt-topic-versioning-and-qos.md)) it will not. Backpressure itself still works, because a blocked send stops the poll loop. The exposure is bounded — roughly 190 in-flight messages — and it is fail-safe for telemetry, and events are protected by the application-level `event.ack` that already exists. `command.result` is the one exposed ledger case, since protocol §5.10 has the device stop retrying once the broker acknowledges. M6 owns the command lifecycle and should decide there whether the edge switches to manual acks.

**`through_device_seq = 0` is ambiguous.** `device_seq` is zero-based, so the value the edge sends when it has committed nothing is indistinguishable from the value it sends when it has committed exactly sequence 0. No unsafe deletion follows — a device asked to discard through 0 discards at most an event the edge does hold — but if the edge ever holds a suffix without its prefix, it will re-acknowledge 0 indefinitely and the device will replay indefinitely. The integration test rewrites the fixture's sequences 118–121 to 0–3 for exactly this reason. Resolving it properly means an explicit "nothing acknowledged" representation in the protocol, which is a §5.13 change and needs its own decision.
