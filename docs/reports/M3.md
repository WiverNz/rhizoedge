# M3 milestone report — Edge Ingestion and SQLite

Completed 2026-08-28. All eighteen M3 issues are implemented and verified. M4 remains READY and was not started.

## Runtime and MQTT ingestion

`edge-controller` owns named MQTT, persistence-pipeline, retention, metrics, and shutdown tasks. A panic or unexpected task exit fails the supervisor; shutdown stops ingress and drains workers to a bounded transaction boundary.

The Edge subscribes at QoS 1 to exactly:

```text
rhizo/v1/devices/+/status
rhizo/v1/devices/+/telemetry
rhizo/v1/devices/+/actuator
rhizo/v1/devices/+/commands/result
rhizo/v1/devices/+/events
```

All five subscriptions are requested after every CONNACK. The bounded ingress channel applies backpressure. The real-broker suite proves ingestion resumes after a Mosquitto restart.

The shared MQTT contract performs envelope, version, kind, and topic/payload identity validation. The injected Edge `Clock` supplies authoritative `received_at`; device time is retained only as advisory metadata.

## SQLite and transactions

The canonical pre-release `0001_initial.sql` establishes the ADR-004 tables,
M3 transport tables, and stable per-sample telemetry effect identity. SQLite
runs in WAL mode with foreign keys, NORMAL synchronous mode, a 5-second busy
timeout, and a four-connection bound. Required measurement, time, batch, dedup,
and replay indexes are present. SQLx offline metadata is checked by CI.

Every message is processed in one transaction: insert the unique message marker, write all accepted effects and outbox state, then commit. A duplicate rolls back and is a normal no-op. Deterministic rollback tests prove there is no durable marker without its effects. SQLite busy failures use three bounded full-jitter retries before failing the message unprocessed.

## Typed telemetry and replay

Each `telemetry.batch` creates narrow typed sample rows. Shared contract validation nulls only an invalid sample's value, retains valid siblings, and records `sensor_invalid`. Unknown forward-compatible kinds remain advisory data. Actuator state remains in its own table.

Replay preserves `event_id`, `boot_id`, `device_seq`, occurrence metadata, and Edge receipt time. Event and message identities both deduplicate. History gaps are durable first-class rows. The cumulative non-retained `event.ack` is published only after commit and advances only through the highest contiguous committed sequence. A lost ACK therefore causes safe replay rather than duplicate history.

## Quarantine, retention, and observability

Malformed messages are stored with topic, bounded diagnostic error, and at most the first 1 KiB of payload. Storage is capped at 1,000 rows and admission is limited to 10 rows per device per minute; decode counters still count suppressed entries.

Retention deletes processed-message markers after 7 days. Every durable effect carries an independent stable identity, including the bounded status high-water projection described below, so no marker has to be kept to hold a logical effect down. Synced outbox rows are deleted after 24 hours, measurements after 90 days, and excess quarantine rows in bounded batches. Commands, watering events, device events, and history gaps are never pruned by M3.

### Post-M3 dedup-retention correction

The pre-M4 audit found that telemetry depended solely on the seven-day transport marker, while actuator and command-result uniqueness surfaced a late duplicate as a constraint error. Telemetry rows now use `(device_id, batch_id, sample_index)` uniqueness so a resealed batch remains one sampling effect; command results use stable `command_id`; actuator paths detect existing `message_id` effects before touching device state; replay detects stable `event_id` sets. A follow-up status audit confirmed that legitimate heartbeats use fresh message ids, so status now uses a bounded per-device `(boot_generation, sequence, current-LWT-id)` high-water projection and all transport markers are prunable. Regression tests remove markers and exercise exact and application-level replays, asserting one logical effect and unchanged current-device timestamps.

Ingestion metrics use constants from `rhizo-telemetry` and bounded labels for message kind, outcome, validation class, task, and gap tier. A cardinality guard keeps the registered series below 100 and rejects device identity labels.

### Post-M3 failure-classification correction

A second pre-M4 audit found that `Classify` was implemented on every error type but called from no runtime site: `EdgeError` was constructed only in its own tests, and the pipeline's retry helper matched `StorageError::Busy` directly. The consequence was a real inversion of [ADR-014](../adr/014-failure-and-retry-policy.md)'s table — a `Permanent` storage failure, which the ADR says must be quarantined and surfaced, instead propagated as a string to the supervisor and exited the process, so one unusable message would have stopped ingestion for every device behind it.

The pipeline now has exactly one message failure site, `apply_classification`, and the classification decides the outcome: `Fatal` propagates and the process exits, `Permanent` quarantines the message through the existing rate limiter and continues, and a `Transient` failure that has exhausted its bounded retries leaves the message unprocessed. A storage failure raised *while* quarantining is classified on its own terms, so a full or broken database still stops the process. `retry_transient` asks `classify().is_retryable()` rather than naming a variant, which is what makes a newly added error variant a compile-time decision at the point it is defined. Its backoff cap was 200 ms and is now ADR-014's documented 500 ms; the base and attempt count were already correct. The event-ack publish path, previously fatal on any `rumqttc` error, is now `EdgeError::Mqtt` and therefore transient — protocol §5.13 makes an acknowledgement advisory and does not require the edge to retry it.

`storage_bytes` was registered but never sampled, so the gauge ADR-004 and [failure-model.md](../architecture/failure-model.md) §3.6 name as the disk-fill signal always read zero. It is now sampled every 60 seconds in the retention task from SQLite's own `page_count` × `page_size`, reporting the main database and not an uncheckpointed WAL.

Tests: `pipeline::classify` asserts each of the three outcomes and that only transient failures are retried, with one attempt plus three retries; `error::classify::storage_defers_to_the_storage_classification` closes a gap where the `EdgeError::Storage` variant had no test of its own; `storage_bytes_reports_a_real_size_that_grows` asserts the gauge is non-zero and moves with the data.

### Post-M3 hardening pass

Four further findings from the same audit were closed before M4.

**The replay acknowledgement could not say "nothing".** `device_seq` is
zero-based, so the old `u64` `through_device_seq` collapsed "sequence 0 is
committed" and "nothing is committed" into the same value, 0. A device that
receives `through_device_seq: 0` discards sequence 0, so the edge was able to
tell a device to delete an event the edge did not hold, and — worse in practice
— a suffix-only replay produced a permanent `0` that never advanced. The commit
result is now `Option<u64>`: `None` publishes **no** acknowledgement at all,
`Some(0)` acknowledges sequence 0 for real. Migration
The canonical baseline makes `replay_progress.through_device_seq`
nullable to carry the same distinction, mapping an existing `0` to NULL only
where sequence 0 was not in fact committed for that boot. Protocol §5.13 gained
a clarifying clause; no field was added, removed, or retyped, so this is not a
wire change. The integration test that renumbered the shipped fixture's
sequences 118-121 onto 0-3 by string replacement is gone: the ACK-0 case is now
tested directly, on the wire, and the unmodified fixture serves as the
suffix-only case it always was.

The honest consequence, recorded rather than hidden: an edge that loses its
`replay_progress` while a device is still in the same boot will never
acknowledge that device's remaining buffer, because it has no prefix and §5.13
forbids claiming one. The device replays indefinitely and eventually opens a
`history.gap`. That is the fail-safe direction, but it is a real operational
edge, and closing it needs a protocol-level resynchronisation.

**`storage_bytes` measured the wrong thing.** After being wired up in the first
correction it still reported SQLite's logical page allocation for the main
database. In WAL mode the log can outgrow the database between checkpoints, and
it is the sum that exhausts the volume, so the gauge now reports the real
on-disk footprint — `db` + `-wal` + `-shm` — via three `stat` calls. An
in-memory database has no files and falls back to page accounting rather than
reporting zero. Sampling stays periodic (60 s), bounded (no scan), and
supervised; a sampling failure that is not already fatal is logged rather than
taking the retention task down with it.

**The SQLx offline gate had almost no subject.** The workspace held exactly one
`sqlx::query!` against 81 runtime-checked `sqlx::query(...)` calls — the
substitution M3-004's Non-goals explicitly forbid — so `cargo sqlx prepare
--check` passed while proving nothing about the queries that carry the
milestone. The entire `crates/storage/src/repo` layer is now compile-time
checked: `ingest.rs`, `quarantine.rs`, `retention.rs`, and `query.rs`, taking
the cache from 1 query to 30. Two exceptions remain and carry their
justification in a comment at the call site: `PRAGMA` statements, which are not
queries over the schema and which sqlx cannot describe, and `migrate.rs`, which
reads `sqlite_master` and the migrator's own `_sqlx_migrations` table before
that table exists. Neither references an application table, so no schema change
can invalidate them.

**SIGTERM had never been run.** M3-018 ticked "SIGTERM exits 0" on the strength
of the supervisor's watch-channel tests, which cover the cooperative drain and
the hung-task timeout but cannot cover a signal handler or a process exit code,
because neither exists outside a process. Those tests remain.
`crates/edge-controller/tests/shutdown.rs` was added alongside them: it spawns
the real binary with its broker deliberately unreachable (failure-model §1.1),
waits until it has migrated and bound its API port, delivers a real `SIGTERM`,
and asserts both `code() == Some(0)` and `signal() == None`. The pair matters —
a binary with no handler is *terminated by* the signal and reports no exit code
at all. It is `#[cfg(unix)]` and compiles to nothing on the Windows development
host, so it is run under WSL2 and the verification evidence below says which
host each command ran on.

## Negative controls

- Replacing Edge receipt time with `device_time_ms` failed the timestamp-authority test (`1756121400000` versus `42000`). Reverted.
- Rejecting an entire mixed-validity batch failed the sibling-preservation test (`New, 0` versus `New, 1`). Reverted.
- Suppressing the explicit reconnect subscription was exercised against a broker restart. Rumqttc's internal request replay kept the black-box test green; explicit per-CONNACK subscription remains in production so recovery does not rely on that client implementation detail.

### Negative controls for the SQLx gate, run during the hardening pass

The point of M3-004 is that the gate fails when it should. That was asserted rather than demonstrated the first time, so both failure modes were provoked and then reverted.

- **A query naming a column that does not exist.** Added `m.nonexistent_column` to `latest_samples`. Compiling against the live schema failed with `error: error returned from database: (code: 1) no such column: m.nonexistent_column`, and `cargo sqlx prepare --workspace --check` failed the same way. Reverted.
- **A valid query change with the cache deliberately not regenerated** — the specific drift `prepare --check` exists to catch. Changed `SELECT count(*) FROM devices` to `SELECT count(*) FROM devices WHERE device_id IS NOT NULL`. An offline build failed with `error: set DATABASE_URL to use query macros online, or run cargo sqlx prepare to update the query cache`, and `prepare --check` failed with `error: prepare check failed: .sqlx is missing one or more queries; you should re-run sqlx prepare`. Reverted, and the cache re-verified as current.

Before the conversion neither control could have failed on 80 of the 81 queries, because they were not checked at all.

### Negative control for the SIGTERM evidence

`an_unhandled_sigterm_kills_a_process_without_an_exit_code` is a permanent one: it asserts that a process which does **not** handle `SIGTERM` reports `signal() == Some(15)` and `code() == None`. Without it, `sigterm_exits_zero` could pass for the wrong reason if the assertion pair were ever weakened to `code() != Some(1)`.

## Deviations from plan

The accepted ADR schema requires a plant identifier on watering rows, while M3 can receive autonomous watering history before M5 plant binding exists. M3 therefore permits a null `plant_id` only for transported offline history; no binding or irrigation decision is inferred. M5/M6 retain ownership of interpretation.

## Known gaps carried forward

One finding from the pre-M4 audit is recorded rather than fixed, and it is a
requirement on M6 rather than a note.

### Mandatory before M6 enables watering: `command.result` durability

**A broker PUBACK is not proof that the edge durably committed a
`command.result`.** The edge sets no `manual_acks`, so `rumqttc` sends the
PUBACK while the message is still in the ingress channel, ahead of the
transaction that persists it. Protocol §5.10 has the device stop retrying once
the broker acknowledges. Between those two facts a result can be acknowledged to
the device and then lost — on a crash, or on a shutdown that drops the channel —
and never republished, because the device believes it was delivered.

The exposure is bounded, roughly 190 in-flight messages, and the other message
kinds are protected: a lost telemetry sample is fail-safe, and offline events
are covered by `event.ack`, which is an application-level acknowledgement
published only after commit. `command.result` has neither protection, and it is
ledger data — it is what tells the edge how much water actually reached the
plant. A silently missed dose under-counts the SAFETY-006 rolling budget in the
permissive direction.

**M6 must close this before real watering is enabled.** Manual acks on the
ingress so the PUBACK follows the commit, a result-level acknowledgement shaped
like `event.ack`, or an equivalent that makes the device's stop-retrying
condition depend on the edge's commit rather than the broker's receipt. Recorded
as a mandatory prerequisite in
[M6-010](../issues/M6/010-implement-command-result-handling.md), in
[PRD 060](../prd/060-irrigation-control-and-safety.md) §Failure modes and
§Acceptance criteria, and in ROADMAP.md §M6 exit criteria.

It is **not** fixed here deliberately: switching the ingress to manual acks
changes when every message kind is acknowledged, and M6 owns the command
lifecycle that determines what the right acknowledgement actually is.
