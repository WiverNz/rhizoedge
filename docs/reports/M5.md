# M5 — Plant Model and Recommendations

**Status:** DONE — 2026-08-29. M5-001 through M5-022 were executed, with M5-020
recorded as superseded before the milestone started, and the exit criteria in
[ROADMAP.md](../../ROADMAP.md) §2 were demonstrated.

## Delivered

**Plants, profiles, and their integrity rules.** `plants` and `plant_profiles`
gained repositories with the two invariants that belong at the storage layer
rather than in one caller: `auto_watering_enabled` is forced to `false` on
insert, whatever path created the plant, and deleting a plant is a **soft
delete** so its `watering_events` survive with their attribution intact.
Deleting a profile that any plant row references is refused and the refusal names
how many — the foreign key is what actually prevents it, so the count includes
soft-deleted plants rather than reporting a profile as free and then failing.

**Profile validation rejects rather than clamps.** Each rule has its own error
variant and its own message naming the value and the limit, so
`dose_ml = 200` against an 80 ml ceiling answers 422 with
`dose_ml (200) exceeds the device hard limit FIRMWARE_MAX_ML_PER_RUN (80)`. The
hard-limit constants are read from `rhizo-mqtt-contract`, so a firmware change
tightens profile validation without a second copy of the number.

**Analysis.** A least-squares moisture trend over a six-hour window that answers
`None` on fewer than five valid samples **and** on samples too clustered to
describe the window; dry-duration accumulated only from observed intervals, with
a gap beyond the freshness threshold resetting rather than filling in;
manual-watering detection from moisture and pot-weight steps, with a rise inside
a completed command's absorption window attributed to that command; bit-identical
stuck-sensor detection raising one event per run; and EC recorded, trended with
the same robustness rules, and warned about — and reaching no decision anywhere.

**The recommendation engine.** The conjunctive rule from PRD 050, with every
conjunct contributing a typed reason whether it passed or failed, so a `no_water`
answer is as explainable as a `water` one. `recommended_ml` is the profile dose
and nothing else. `confidence` is reported and is an input to no decision.

**Plant state, separate from irrigation state.** Derived from the recommendation's
own reason codes, so the state and the sentence an operator reads cannot
disagree. Transitions are persisted; steady state is not. A monitoring-only plant
reaches `water_recommended` and stays there, which is exactly what somebody with
a watering can needs to see.

**The ADR-016 configuration model, end to end.** Sensor bindings with
`control`/`required`/`advisory` roles validated against declared capabilities;
at most one `control` binding, refused from removal while automation is on;
leak and tank forced to `required` on any plant with an actuator; an optional
actuator binding whose absence is normal. Per-plant, per-kind measurement
policies with nested warning and critical bands, seeded from a profile once and
never re-derived. Threshold evaluation with hysteresis and confirmation raising
one event per transition, for plants with and without a pump, and actuating
nothing.

**Offline policies authored, not published.** A candidate is derived from the
plant's own bindings and measurement policies and validated by
`rhizo_policy::validate_authored`, which delegates every numeric rule to the
contract's `OfflinePolicy::validate` — the function the firmware calls — and adds
exactly one thing: an authored policy is checked **even while disabled**, because
`enabled` defaults to `false` and an operator needs to learn the limit while they
are typing it. A plant with no actuator is refused a policy outright.

**A species preset catalogue.** Twenty-two curated entries compiled into the
binary, versioned, and queryable with no network and no database. Every
preference value is labelled `source_fact` or `rhizo_default`; there is no third,
unlabelled case, and a value without a `provenance` tag does not deserialise.
Tests assert over the whole catalogue that no field is an interval, frequency, or
schedule, and that no field names a device, sensor, point, or capability.
Applying a preset writes ordinary `MeasurementPolicy` rows resolved against the
plant's **existing** bindings, records provenance columns nothing reads, and gets
out of the way.

**The remaining battery wire surface, and a device that sleeps.**
`MeasurementKind::BatteryVoltage` and `BatteryPercent` as ordinary advisory kinds
that are explicitly *not* control-eligible; `device.config.power` with its four
optional fields and an absent block meaning always-on; a typed `wake_reason`; and
`wake_interval_seconds` validated against the same constants the status side
publishes, rejected rather than clamped. The simulator gained `--power-mode
battery` with a real wake cycle, a battery model, and the two faults SCEN-111 and
SCEN-112 need.

## Verification

The full gate passed: `cargo fmt --all --check`; `cargo clippy --workspace
--all-targets --all-features -- -D warnings`; `cargo test --workspace
--all-features`; both `thumbv7em-none-eabi` no-default-features builds of
`rhizo-mqtt-contract` and `rhizo-policy`; `cargo sqlx prepare --workspace
--check` against a database with all nine migrations applied; `docker compose -f
deploy/docker-compose.yml config`; `cargo run -p rhizo-docscheck`; and
`git diff --check`.

`cargo test --workspace --all-features` reports **834 passed, 0 failed, 1
ignored** — the ignored test predates M5.

The required broker suites ran against live Mosquitto with
`RHIZO_REQUIRE_BROKER=1`, so nothing skipped:
`cargo test -p device-simulator --test integration`,
`--test safety_007`, `--test battery_wake_cycle`, and
`cargo test -p edge-controller --test integration -- --test-threads=1`.

**The exit criterion that defines the milestone.** `no_commands_in_m5` runs a
complete drying cycle through a real edge against a real broker, with a
subscriber on `rhizo/v1/devices/+/commands/#` for the whole run. The plant
reaches `water_recommended` with a non-empty structured reason list including
`moisture_below_target` and `dry_for`, and **not one message appears on any
command topic**; `commands` and `watering_events` are both empty afterwards. The
loop that produced it takes no MQTT client at all, which is the strongest form
the promise can take.

Every other exit criterion was demonstrated by a named test:
`POST /water` on a plant with no `ActuatorBinding` returns **422**
`no_actuator_bound` and not 409, while the same plant keeps its telemetry,
policies, and alerts; a binding naming an undeclared capability is refused; a
critical temperature raises an alert and changes no watering answer; a profile
with `dose_ml = 200` is refused with the firmware limit named; a moisture step
following a completed command creates no second event; a preset-configured plant
has ordinary editable policy rows, still has `auto_watering_enabled = false`, and
no catalogue entry contains a schedule; and a simulated battery device sleeps,
shows as `sleeping`, goes `isolated` when it stops waking, and fires its Last
Will when it leaves without announcing.

**One flaky assertion was made order-independent rather than retried away.**
`a_sleeping_device_leaves_a_retained_sleep_announcement` originally read
whichever retained status happened to be on the topic. A preceding test's device
can leave a retained will there, so the assertion depended on the order the
harness chose. It now resubscribes in a bounded loop until the sleep
announcement appears — the device republishes one every wake — and the test was
run three times in a row to confirm it.

**Negative controls.** Three mutations were applied and reverted. Removing the
sparsity check from `trend::fit` made
`five_clustered_samples_are_refused_for_sparsity` fail. Making the dry-duration
accumulator count across a gap made
`a_gap_longer_than_the_staleness_threshold_does_not_accumulate` fail. Dropping
the command-attribution branch from `detect_manual_watering` failed both
`a_step_following_a_completed_command_creates_no_event` and the integration test
of the same name. Each mutation was reverted and the tests returned green.

## Corrections made during the milestone

**Foreign-key violations were classified `Fatal`.** `StorageError::from_sqlx`
matched SQLite's *extended* result codes one at a time — `19`, `1555`, `2067` —
so a foreign-key violation, which is `787`, fell through to `Database` and
therefore to `FailureKind::Fatal`. A caller would have retried a write that can
never succeed. The classification now masks to the primary code, which covers
every flavour of `SQLITE_CONSTRAINT` including the ones SQLite has not added yet.

**An absent `device.config.power` block was retiring battery mode.** The
simulator read the incoming block with `unwrap_or_default()`, which turns an
*absent* block into an explicit `always_on` — so the first retained
`device.config` a broker held from before ADR-018 silently stopped a battery
device from ever sleeping. It is the same distinction the edge already draws on
the status side, and getting it wrong here would have been invisible in the
field: the device would simply never sleep and nobody would know why. Caught by
the real-broker suite, which is the only place a stale retained configuration
exists; `a_configuration_with_no_power_block_does_not_retire_battery_mode` now
pins both directions, and the broker test asserts the mode survives the
subscribe.

**Sleeping is a clean disconnect.** The first implementation dropped the socket
after publishing the announcement, exactly as the `disconnect` fault does. The
broker then published the Last Will, which **overwrote the retained sleep
announcement with `connection_lost`** — turning every expected absence into an
unexplained one. It was caught by the real-broker test rather than by the
in-process one, which is the reason that test talks to Mosquitto.
`Connection::disconnect_cleanly` now leaves without saying anything, and
`sleep-without-announcing` is the one path that still drops the socket.

**A preset rejection reports the rule, not the preset.** `PresetError::code`
originally answered `preset_violates_profile_limit`. An operator needs to know it
is the firmware dose ceiling, and that the answer would have been the same had
they typed the number by hand, so the code is now the inner rule's.

**Prose is rendered in one function, and stored with the row.** Reason text is
produced by `reason_text`, called from exactly one place, and the sentence is
persisted alongside the code so a recommendation keeps the wording it actually
showed.

## Deviations from the issue text

**`missed_wake_count == 2` after `miss-wake:2` is unreachable, and the reason is
M4's.** A missed wake announces nothing, so it opens no new window, and the
liveness timer counts at most one miss per window — the rule M4's own
`each_sleep_cycle_can_miss_at_most_once` asserts. Two consecutive missed wakes
therefore leave the device `isolated` with `missed_wake_count == 1`, which is
what `a_simulated_sleeping_device_is_sleeping_then_isolated` asserts against a
real broker. The alternatives were a device that wakes far enough to re-announce
a sleep it is not taking, or a counter that runs away on one window; neither is
better than an honest one. The safety-relevant half — `isolated` — is unaffected.
The criterion in ROADMAP.md §2 was corrected in the same change.

**M5-019's registry source-switch is contingent on a publisher that does not
exist.** The issue asks that, "once the edge publishes `device.config`", the
registry take `power_mode` and `wake_interval_seconds` from configuration rather
than from the device's declaration. The wire surface is delivered and validated;
**no config publisher exists in M5** — it is M6's — so the registry's source is
unchanged and the sentence in `http-api-boundaries.md` §2.3 and PRD 040 F-040-20
now says so plainly rather than naming M5-019 as the moment it changes. Building
the switch now would mean building the half of it nothing can exercise.

**M5-014's documented verification filter names a module that is not there.** The
issue's Verification section says `cargo test -p edge-controller api::policies`
while its Files-likely-affected section says
`crates/edge-controller/src/api/measurement_policies.rs`. The file name was
followed, so the filter is `api::measurement_policies`. Recorded here rather than
silently renaming either.

**M5-020 was not implemented.** It is wholly superseded by the dated post-M4
battery-compatibility correction and its review, both recorded in
[M4.md](M4.md); SAFETY-021 is enforced in M4. Nothing in it was outstanding, and
M5 added a *producer* for the behaviour it describes rather than the behaviour
itself.

## Boundaries

M5 issues no commands. There is no safety gate, no irrigation state machine, no
command lifecycle, no offline evaluator, and no policy publisher; `POST /water`
exists only so that SAFETY-018's refusal is distinguishable, and it answers 501
for a plant that does have an actuator. `resolution=minute|hour|day` on the
measurements endpoint answers 501 until M13-010 adds downsampling. The simulator
still contains no evaluator, no decision type, and no dose scheduler, and
`tests/single_actuation_path.rs` remains green. Firmware deep sleep is M9's; the
simulator's wake cycle is the behavioural specification M9-019 matches.
