# M6 — Irrigation Control and Safety

**Status:** DONE — 2026-08-31. M6-001 through M6-024 were executed and the exit
criteria in [ROADMAP.md](../../ROADMAP.md) §2 were demonstrated.

This is the milestone where the software can move water. Everything before it was
observation; from here a defect changes from a wrong number on a screen to water
on the floor.

## Delivered

**The safety gate, and the shape that makes it hard to get wrong.**
`rhizo_domain::irrigation::gate::safety_gate` is an ordered veto with no
catch-all arm on any safety input. Every `match` spells out each variant, so
adding a `LeakState::Degraded` fails to compile until someone classifies it; a
test reads the file and fails if a `_ =>` appears. The order is the documented
one — actuator, leak, leak-unknown, sticky lockout, reconciling, tank-unknown,
tank-low, tank-stale, required measurements, sample-absent, sample-invalid,
sample-stale, daily cap — and the two reasons an operator is shown are kept
apart on purpose: `Uncertain` for what the edge cannot read, `TankLow` for what
it measured, which is the same distinction protocol §5.8 step 7 draws.

**The manual exception is exactly two checks wide.** `mode: "manual"` skips
`SensorFault` and `StaleData` and nothing else. It is still refused by a leak, a
low or stale reservoir, an exhausted rolling window, an explicit lockout, and an
incomplete reconciliation. `mode: "recommended"` does **not** inherit the
privilege: accepting the engine's advice is not a claim to have looked at the
plant, and the advice was computed from data that must still be fresh.

**The state machine as a pure, total function.** `evaluate` takes the gate as its
first statement, reads no clock, performs no I/O, and answers for every (state,
input) pair — including `NaN`, absent readings, and impossible combinations, all
of which resolve to a lockout. `prop_state_machine_total` asserts it. Every row
of PRD 060's normative transition table has a named test, and `next_state` is
that table's "To" column, split out so the caller can persist it in the same
transaction as the side effect.

**The rolling 24-hour cap, derived from rows.** There is no counter anywhere. The
window sums `watering_events` inside `now - 24h` for the budgeted modes and adds
the conservative credit carried by commands that settled without delivering:
`interrupted` and `failed` charge their full `requested_ml` and create no
watering event, so the sum alone would under-count them. Checked twice — once
before a dose is chosen, once with the dose included — so a dose that would cross
the cap is never issued at all.

**The command lifecycle, in the order that is the safety property.**
`[TX: commands row 'issued' + irrigation transition + outbox] COMMIT` → publish
QoS 1 with `retain = false` → record `published_at`. `command_id` is the primary
key, so a duplicate insert fails at the storage layer rather than at a
check-then-insert race. A publish is retried three times with a 200 ms base and a
2 s cap, **always with the same payload**: the payload is built once, before the
first attempt, and a test asserts that the retry loop cannot reach an id
allocator at all. After three failures the command is `failed`, the plant returns
to `Recheck`, and no watering event exists.

**Result handling that never invents a watering event.** `completed` creates
exactly one; `rejected`, `interrupted`, and `failed` create none. A result for a
terminal command writes nothing, and a result for a command this edge never
issued is logged and ignored — the edge does not create a row to match it.

**The M3 gap, closed.** A broker PUBACK was not proof of a durable commit: the
edge set no `manual_acks`, so `rumqttc` acknowledged while the message was still
in the ingress channel, ahead of the transaction that persists it, and protocol
§5.10 stops the device retrying at the PUBACK. `command.result` is ledger data
and had neither telemetry's fail-safe loss nor `event.ack`'s application-level
acknowledgement. The ingress now sets `manual_acks`, and the pipeline sends the
PUBACK **after** `process` returns — that is, after the commit. A permanently
unparseable message is quarantined *and* acknowledged, because redelivering it
for ever would wedge every device behind it; a transient failure is not
acknowledged, so the broker redelivers.

**Restart reconciliation.** On boot, `issued`/`in_flight` commands are expired
past their TTL or awaited inside it, irrigation state is restored exactly
including `wait_until` and `doses_this_cycle`, and **nothing is re-published**.
`Recovery::republished` is a field that is asserted to be zero rather than a
comment saying so.

**Clock-step detection.** Each tick samples `Instant` beside the wall clock;
comparing the wall clock against itself cannot reveal a step. A forward step
beyond ten minutes locks every plant `Uncertain` for one cooldown, which needed a
new mechanism — `Uncertain` is auto-clearing and would lift on the very next tick
— so `plants.lockout_until` holds it. A backward step is recorded and nothing
else: it makes the rolling window include *more* history, which is conservative
on its own.

**No-delivery detection.** Two doses with no moisture rise **and** no weight rise
lock the plant `NoDeliveryDetected`, which needs an explicit clear. Requiring
both signals avoids the obvious false positive — near field capacity the soil may
not read wetter although the pot is plainly heavier — and unreadable evidence
counts as no response, so uncertainty stops the cycle rather than continuing it.

**The REST surface, with 409 as the safety answer.** `POST /water` returns 202
with a `command_id`, or 409 carrying `{ reason, since, clearable, message }`, or
422 `no_actuator_bound` for a monitoring-only plant — the distinction SAFETY-018
requires. `lockout/clear` refuses while the condition is active, and a leak reset
additionally requires the signal to be **positively** `Clear`: a silent sensor
cannot demonstrate a dry tray. There is no override, force, bypass, expedite, or
wake parameter; every body is `deny_unknown_fields`, so one would be a 422 rather
than a silently ignored field, and a structural test greps the API directory.

**Device configuration, retained.** `PUT /devices/{id}/config` validates, bumps
`config_version`, and publishes retained — the one place `retain = true` appears
for a device topic besides policy. A configuration violating a range or a
firmware limit is rejected with 422 rather than clamped, and a body naming a
safety limit is refused at the boundary even though the device would ignore it.
Lost retained state triggers republication of every configured device; a device
the edge never configured is not handed a fabricated version.

**The single shared offline evaluator.** `rhizo_policy::evaluate_offline` is the
one implementation of the offline rules: the ordered gate (enabled, valid, leak,
tank, pump, required, control, budget, doses), then confirm → dose → absorb →
recheck → cooldown with hysteresis and a bounded dose count. It is pure,
`no_std`, allocation-light, and the crate cannot read a clock — a test asserts
that, with the needles split so the assertion list does not match itself. The
simulator calls it from **exactly one place**, and
`tests/single_actuation_path.rs` now asserts *one* call site where it previously
asserted zero.

**Autonomous doses reach the pump through the same path.**
`Device::autonomous_dose` applies `rhizo_mqtt_contract::safety::bound_dose` —
protocol §5.8 steps 10-12, extracted so the commanded and autonomous paths share
one implementation of the firmware ceilings — and then reaches the same
`begin_dose`, the same in-flight NVS write before actuation, the same
`start_pump`. Steps 2 and 3, `clock_unsynced` and `expired`, are deliberately
absent: they are properties of a *command* issued by another machine at a
wall-clock instant, and SAFETY-015 says plainly that it governs the autonomous
path while SAFETY-002 governs the commanded one.

**Reconciliation, and the hold that makes it safe.** A device replaying buffered
history holds its plants in `Uncertain` until the edge has committed a contiguous
prefix through the device's final batch. Replay is idempotent on `event_id`, so
reconnecting mid-replay creates no duplicates, and autonomous doses land in the
**same** rolling window as commanded ones — one budget per plant, not one per
control path.

**Durable command intents for sleeping devices.** A `POST /water` to a sleeping
device publishes nothing, persists an intent, and returns 202 with
`pending_for_device_wake` and **no `command_id`** — the field is absent rather
than null, so a client that reads it unconditionally fails loudly. At the next
wake the edge publishes `edge.time`, re-runs the **whole** gate against current
inputs, and mints one command whose `issued_at` is the wake instant. At most one
open water intent per plant, enforced by a partial unique index as well as by a
409. `commands` gained no column.

### The three verifications M6-024 says carry the weight

**1. `POST /water` during a leak returns 409 and publishes nothing.**
`safety_003_leak_blocks_manual_api_with_nothing_published` holds a spy subscriber
on `rhizo/v1/devices/+/commands/#` for the whole run, asserts the 409 and its
structured body, and then asserts the spy saw nothing. `commands` and
`watering_events` are both empty afterwards.

**2. Killing the edge after publish and restarting produces no second command and
exactly one `watering_event`.** `restart_mid_command` starts an edge, issues a
dose, confirms the command reached the broker unretained, and then drops the
edge — aborting ingress and pipeline mid-flight. A second process opens the same
durable database, runs the recovery procedure, and the spy sees nothing further.
The device's result then settles into one event, and `commands` holds one row.

**3. `PROPTEST_CASES=10000 cargo test safety_006` passes.** It generates
adversarial histories containing restarts between publish and result, forward and
backward clock steps, interrupted doses credited conservatively, and duplicate
results, and asserts the window against the **ledger's own timestamps** rather
than against a stepped wall clock — see §Deviations for why that is the stronger
claim.

### Every other exit criterion, by name

- **SCEN-002's full cycle** — `a_full_cycle_waters_a_real_simulated_plant` runs a
  real simulator against a real broker, waits for reconciliation to complete
  (which is SAFETY-016 observed in passing), and asserts the documented next
  state and a rolling total inside the cap.
- **A duplicate command actuates once** —
  `safety_001_duplicate_command_single_actuation` publishes three identical
  results with distinct `message_id`s, so transport dedup cannot do the work the

- **Nothing retained on a command topic** — `no_retained_commands` connects a

- **A plant with no tank sensor never receives a dose** — the gate answers

- **A stale plant is blocked automatically and can be watered manually** —
  `manual_watering_succeeds_under_sensor_fault_but_not_under_leak`, with the

- **Clearing a leak while active returns 409** — and so does clearing one while

- **No `_ =>` arm on any safety match** — asserted against the gate's source in
  both crates.
- **Replaying a buffered batch three times out of order** produces one
  `watering_event` per `event_id` and one budget charge.
- **A sleeping device's `POST /water`** publishes nothing, returns
  `pending_for_device_wake` with no `command_id`, survives an edge restart, and

## Corrections made during the milestone

**An empty complete replay held the plant for ever.** The first implementation
read "the sender says complete but the edge holds no contiguous prefix" as a hole
and kept the plant in `Uncertain`. A device that was never isolated buffers
nothing, replays an empty batch, and produces exactly that shape — so every
ordinary reconnection would have frozen its plants permanently, and the real
simulator found it in the first end-to-end run. `is_reconciling` now separates
the two: a *suffix with no prefix* keeps the hold, because the edge is holding
history it cannot vouch for the start of; an *empty* complete replay releases,
because the device had nothing. Both are asserted.

**The reconciliation hold could not live in `devices.connectivity_mode`.**
`persist_status` rewrites that column on every heartbeat, and a device replays
*while* it is heartbeating — so a hold kept there would be cleared by an
unrelated status message, which is not a hold. It is now derived from
`replay_progress` scoped to the device's current `boot_id`, which survives a
restart, cannot be cleared by a status, and does not hold a plant for ever after
a reboot abandons an old replay.

**`elapsed` had to be a delta, not a since-boot instant.**
[offline-autonomy.md](../architecture/offline-autonomy.md) §4's signature comment
said "since boot", but §5 stores the cooldown as a **remaining duration** and
never as an absolute deadline — a device that may have no absolute time cannot
interpret one after a boot. With remaining durations on one side and an instant on
the other there is nothing to subtract. §5b settles it: `credit_elapsed(...) ->
Duration` returns exactly what the evaluator needs, and a reset that cannot be
credited returns `Duration::ZERO`. The §4 comment was the stale half and has been
corrected; the essential property — never a wall clock, always a parameter — is
unchanged, and crediting zero is what a reboot does.

**Foreign-key-shaped test fixtures.** `command_intents.command_id` really
references `commands`, so a delivery test needs a command to point at. That the
key bites is the point: an intent may only ever name a command the edge actually
minted.

**Self-referential structural tests.** Four tests scan their own file for a
forbidden shape and initially matched their own assertion lists. Each now scans
only the production half, split at `#[cfg(test)]`, or splits the needle — a
self-scanning test that trips on itself proves nothing about the code it is
scanning.

**Two order-dependencies were made order-independent rather than retried away.**

The first was mine: `metrics::control` asserted an exact `before + 1` delta on
two process-wide series. The Prometheus registry is a `OnceLock` singleton, so
any concurrently running test lands in the same counter and the assertion failed
on timing rather than on behaviour. Both now assert *strictly greater*, which is
the honest claim for a shared counter.

The second was pre-existing and this milestone made it visible.
`support::broker`'s lock serialises tests inside one binary, and an edge
subscribes to the whole `rhizo/v1/devices/+/#` tree — so a second test *binary*
driving `plant-node-01` writes into the first one's database. Adding a third
broker-backed binary turned a rare flake in M4's
`intentional_sleep_and_duplicate_each_receive_edge_time` into a frequent one. The
M6 suite moved to the second provisioned account, `plant-node-02`, which removes
the collision instead of widening a timeout.

`restart_mid_command` also needed its premise made real: it originally dropped
the edge immediately after `POST /water` returned, which sometimes aborted
`rumqttc`'s event loop *before* it had written the publish to the socket. That is
the "publish failed" path, not the one SAFETY-010 is about, so the test now waits
for the spy to observe the command — matched on its `command_id`, not merely on
the topic — and kills the edge after that.

## Deviations from the issue text

**`IrrigationInputs` has six fields PRD 060's illustrative struct does not.**
Each is required by a normative requirement the struct predates, and each is
documented at its declaration:

| Field | Why |
|---|---|
| `dry_duration` | The transition table defines `Drying → DryConfirmed` as `dry >= dry_confirm_minutes`, and no other field carries it. The alternative was a partial function, which F-060-11 forbids. |
| `pre_dose_weight` | F-060-33 compares "no moisture **and** no weight response"; two baselines need two fields, and the struct supplies only `pre_dose_soil`. |
| `required_inputs` | SAFETY-017's edge half. Without it a plant that declared pot weight `required` would water on a silent scale. |
| `active_lockout` | Without it no explicit-clear lockout could outlive one tick, and F-060-41 would have no mechanism. |
| `lockout_held_until` | F-060-51's only mechanism: `Uncertain` is auto-clearing and would lift on the tick after a clock step. |
| `reconciling` | SAFETY-016, which postdates the struct. |

The tuning constants the machine runs on — dose, cap, cooldown, absorption,
recovery delta, tank floor, command TTL — arrive through `AutomationPolicy`
rather than as a `profile` field, because ADR-016 makes a `PlantProfile` a
**template** that seeds a plant once. A machine that read a profile at evaluation
time would make editing a template silently rewrite twelve plants' watering
rules.

**`EvaluationMode` has three variants, not two.** PRD 060's comment lists
`Automatic | ManualRequest { ml }`, but F-060-05 says "`manual` mode skips only
…", the budget query names `recommended`, and `http-api-boundaries.md` §2.6
defines `mode ∈ manual | recommended`. Three modes is the coherent reading of the
three documents, and `recommended` deliberately does not inherit the manual
privilege.

**`PlantProfile` gained three fields.** `recovery_delta_vwc`, `tank_min_percent`,
and `command_ttl_seconds` are all named by PRD 060 and by
[configuration-model.md](../architecture/configuration-model.md) §PlantProfile,
and none of them existed on the type. They deserialise with the documented
defaults, so a profile document written in M5 keeps its meaning.

**The no-catch-all rule is asserted by a source scan, not by `trybuild`.**
M6-002's Tests-required section asks for a compile-fail test. The property it
protects is already enforced by the compiler — the matches are exhaustive, so
adding a `LeakState` variant genuinely fails to build — and a `trybuild` case
would add a dev-dependency and a fixture crate to assert what `rustc` already
asserts. What a compile-fail test would *not* catch is a `_ =>` arm added to make
the build pass, which is the real risk, so `safety_012_no_catch_all_arm_on_a_safety_match`
reads the gate's source and fails on one. Both crates' gates are covered.

**M6-013's "drift detection landed in M4-006" is accurate and unchanged.** M6
adds the publisher; the drift comparison is M4's and was not touched. M5-019's
registry source switch — taking `power_mode` and `wake_interval_seconds` from
configuration once a publisher exists — remains **not** implemented: M6's
publisher writes `desired_config_version` and the retained payload, and switching
the registry's source is a registry change with its own semantics that no M6
issue asks for. It stays recorded where M5 left it.

**One migration was added rather than the baseline being edited.**
`versioning-policy.md` §4 permits squashing into `0001_initial.sql` before the
first release, and M5 did that. M6 is additive and arrives as
`0002_irrigation_control.sql` instead, so an existing development database
upgrades in place — and the backup path in `migrate::run` is now exercised by a
real version change rather than only by a fresh create.

**The metrics cardinality guard moved from 100 to 220, with the arithmetic
written down.** `irrigation_state_transitions{from,to}` is seven states crossed
with seven, which is forty-nine series in the worst case and is bounded because
the state vocabulary is. Adding eighteen command outcomes, twelve lockout
reasons, nine refusal reasons, and the M3–M5 catalogue puts the honest headroom
near two hundred. A companion assertion now names the failure the guard actually
exists for: no metric but the device-restart counter may carry an entity id.

**The `manual` mode is outside the automatic rolling cap.** M6-007 states it
(`mode IN ('automatic','recommended')`), and M5's `delivered_since` counted every
mode but `detected`. The M6 query follows M6-007. A person who waters manually
has taken responsibility for it; the device's own `FIRMWARE_MAX_DAILY_ML` still
bounds the total, and the manual dose still resets the cooldown through
`last_watering_at`.

**An ambiguous autonomous dose is charged to every actuator-bound plant.** A
`watering.offline_autonomous` event names a policy version and a volume, not a
plant, and the plant is resolved from the actuator bindings on that device. One
bound plant is the ordinary case and the attribution is exact. With several, the
dose is charged to all of them and the ambiguity is logged: over-counting reduces
future doses, under-counting would permit an extra one, and the conservative
direction is the same one PRD 060 §Open questions 2 picks for an interrupted
dose.

## Boundaries

M6 adds no cloud behaviour: `rhizo-domain` still does not depend on
`rhizo-cloud-client`, `IrrigationInputs` has no field derived from cloud state,
and `safety_009_no_cloud_input_reaches_a_watering_decision` asserts both. The
outbox rows M6 writes are history for M7 to drain and are never read by a
decision.

Firmware deep sleep remains M9's; the simulator's wake cycle is still the
behavioural specification M9-019 matches. `SAFETY-011`, `SAFETY-019`, and
`SAFETY-020` remain firmware-owned and are unchanged. The hardware halves of
`SAFETY-007` and the real-sensor halves of `SAFETY-003` and `SAFETY-004` are
M11's.

No UI exists (M12). `resolution=minute|hour|day` on the measurements endpoint
still answers 501 until M13-010.
