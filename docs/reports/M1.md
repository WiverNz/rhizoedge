## Compatibility corpus

The fix-up below replaced the original harness. Final state:

| | Count |
|---|---|
| Valid fixtures | 16 |
| Invalid fixtures | 11, in 10 failure classes |
| Message kinds with a valid fixture | 11 of 11 (enforced by test) |

**Valid fixtures** are discovered from `test/fixtures/protocol/valid/`, dispatched
on the envelope `kind`, and decoded into the **concrete payload type** —
`TelemetryBatch`, `ActuatorState`, `DeviceEventBatch`, `DeviceStatus`,
`DeviceConfig`, `OfflinePolicySet`, `EdgeTime`, `WaterCommand`, `TareCommand`,
`CalibrateCommand`, `CommandResult`. Each then runs that payload's own semantic
validation, and every JSON path stated in the file must survive a re-encode with
its value intact. A type may add a field the fixture omits (a `serde` default); it
may never lose or alter one the fixture states.

**Invalid fixtures** live in a directory named for the failure they prove, and the
test asserts that exact typed variant: `DecodeError::Envelope`,
`DecodeError::UnsupportedVersion`, `DecodeError::Json` plus a §2 grammar check for
device-id/topic injection, `BatchError::Empty`, sample `unit` and `value`
validation-report fields, `PolicyError::DoseAboveHardLimit`,
`PolicyError::InvalidHysteresis`, `PolicyError::NonScalarControlKind`, and
`EventBatchError::DuplicateEventId`. A directory the harness does not recognise is
a hard failure, never a silent skip.

Both halves are directory-driven: another fixture for an existing message kind or
failure class needs no Rust change.

## The fix-up, and why it was needed

The original M1 harness decoded valid fixtures only as
`Envelope<serde_json::Value>`. That verified the envelope and **never the
payload**, so any payload field could have been renamed with the whole suite still
green — the precise failure an append-only corpus exists to prevent. It also
enumerated invalid fixtures by hard-coded filename and asserted only `is_err()`
rather than the documented variant, and both fixture issues' `Verification` block
ran `cargo test -p rhizo-mqtt-contract fixtures::`, a filter that matches **no
test** in an integration-test binary and therefore exited 0 without running
anything. Several early fixtures were empty stubs (`"policies": []`,
`"events": []`, empty capability arrays) that exercised no structure at all.

Filling those stubs is a deliberate, one-time exception to the append-only rule,
taken while no v1 device exists. It does not apply again.

## Protocol clarifications

Three fail-closed behaviours in `validate_water_command` were correct but
undocumented, and undocumented divergence is still divergence. §5.8 now names its
non-finite inputs explicitly, and one implementation outcome was corrected to
match the semantics rather than the other way round:

| Input | Was | Now | Rationale |
|---|---|---|---|
| non-finite `tank_level_percent` | `TankLow` | **`TankUnknown`** (step 7) | An unreadable level is *unknown*; `TankLow` is a **measured** condition. §4 forbids emitting `NaN`, so one arriving means the reading is unusable. |
| non-finite `tank.min_percent` | *unchecked* — `value <= NaN` is false, so the tank gate silently passed | **`TankUnknown`** (step 7) | Found during this audit. An unusable threshold means the tank condition cannot be evaluated at all (SAFETY-012). |
| non-finite or ≤ 0 `pump.ml_per_second` | undocumented `PumpUnavailable` | documented `PumpUnavailable` (step 9) | Step 12 divides by it; a device that cannot compute a bounded run duration has an unavailable pump, and must refuse before the division. |
| non-finite `delivered_today_ml` | undocumented `OverDailyMax` | documented `OverDailyMax` (step 11) | `NaN + x > max` is false, so without the guard a `NaN` accumulator *grants* the dose. A device that cannot prove it is under budget assumes it is not. |

The ordered 12-step gate is otherwise unchanged. §5.8 gained a normative paragraph
stating the general rule: non-finite guard inputs are `Unknown`, never permission.
Covered by `safety_012_nonfinite_guard_inputs_are_unknown_not_permission`.

## Policy validation cleanup

`PolicyError::DisabledActuatorPresent` existed but was never constructed. §5.11 is
explicit that removing a plant's policy is an `enabled: false` republish at a
higher `policy_version`, **not** an omission — so a disabled policy normally
retains its actuator binding and thresholds. The variant asserted a rule the
normative model forbids from ever occurring, and was **removed**.
`disabled_policy_retaining_its_actuator_is_valid` pins the documented shape, and
`policy-disabled.json` is now that shape on the wire rather than `"policies": []`.

## Measurement eligibility

`MeasurementKind::LeakState.control_eligible()` returned `true`, yet a policy's
control measurement carries `trigger_below`, `resume_above` and
`confirm_duration_ms` — numeric-threshold semantics with no meaning for a boolean.
ADR-015 §4 and offline-autonomy.md make leak a **veto at gate step 3**, never a
trigger.

The old predicate conflated two questions. They are now separate:

- `is_known()` — does this contract version recognise the kind? Drives
  `advisory_only`, per §5.1: an *unrecognised* kind is stored but never gates
  actuation. A healthy `leak_state` sample is recognised and still gates.
- `control_eligible()` — may the kind be a policy's primary control measurement?
  Now requires a recognised **scalar** kind, so `LeakState` is `false`.

Policy validation gained `NonScalarControlKind` alongside `UnknownControlKind`, so
the two failures stay distinguishable. Documented in §5.11's field table and
offline-autonomy.md; covered by `control_measurement_must_be_a_known_scalar_kind`,
`advisory_and_control_eligibility_are_independent`, and the
`policy_non_scalar_control_kind/` fixture.

## Amendment — post-M2 protocol seam cleanup (2026-08-28)

The counts above were correct when M1 shipped and are left as the record of
that milestone. The protocol has since grown one topic and one message kind:

| Was, at M1 | Is now |
|---|---|
| 11 concrete topic forms | **12** — `rhizo/v1/devices/{id}/events/ack` added |
| 11 message kinds | **12** — `event.ack` added |
| 16 valid fixtures | 20 currently, including 2 `event.ack` fixtures |
| 11 known measurement kinds | unchanged at 11 |

`event.ack` closes protocol §5.4's retain-until-acknowledged requirement, which
M1 recorded as having no wire mechanism. See mqtt-v1.md §5.13 and
`docs/reports/M2.md` §Amendment.
