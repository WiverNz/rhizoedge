# ADR-005 — Cloud event model, PostgreSQL schema, and idempotency

## Status

Accepted — 2026-08-25. Implemented in M7.

**Extended 2026-08-26.** The event catalogue gains offline-autonomy kinds, and
the cloud `measurements` projection follows the narrow typed-kind shape
([ADR-017](017-extensible-measurement-model.md)). The idempotency mechanism —
`(edge_id, event_id)` with `ON CONFLICT DO NOTHING` — is unchanged, and is
exactly what makes forwarding replayed offline history safe.

## Context

The edge ships history to the cloud over an unreliable link. Retries are
guaranteed: a request may succeed on the server and time out on the client, so
the edge cannot distinguish "not delivered" from "delivered, ack lost". The only
safe posture is at-least-once delivery with exactly-once *effect*.

The cloud must also tolerate replay of weeks of backlog after an outage without
creating duplicate history, and must be structured for multiple edge instances
from the start ([ADR-003](003-edge-first-ownership-model.md)).

## Decision

### Events, not entity upserts

The edge sends immutable **events**, not "here is the current state of plant X".
An event is a fact that happened at a time, and facts are naturally idempotent:
applying the same fact twice is applying it once.

```json
{
  "event_id": "018fd6c4-7b4a-7c31-9e2a-3f5b1d8c6a20",
  "edge_id": "home-01",
  "kind": "measurement.sample",
  "occurred_at": "2026-08-25T11:30:00Z",
  "device_id": "plant-node-01",
  "plant_id": "monstera-01",
  "payload": {
    "point": "default", "kind": "soil_moisture",
    "value": 31.7, "unit": "vwc_percent", "quality": "ok",
    "batch_id": "018fd6c4-7b4a-7c31-9e2a-3f5b1d8c6a20"
  }
}
```

Event kinds in V1:

```text
measurement.sample                              typed kind (ADR-017)
device.status           device.event            device.config_applied
device.capabilities     device.policy_applied
device.isolated         device.reconciled       history.gap
plant.created           plant.updated           plant.state_changed
plant.binding_changed   plant.policy_changed
watering.started        watering.completed      watering.detected
watering.offline_autonomous                     delivered while isolated
command.issued          command.settled         lockout.set   lockout.cleared
threshold.warning       threshold.critical      fertilisation.applied
```

### Idempotency key: `(edge_id, event_id)`

`event_id` is a UUIDv7 generated by the edge when the event is written to the
outbox, inside the transaction that produced it. It is stable across every
retry — this is the crucial property. An `event_id` regenerated on retry would
defeat the entire mechanism.

The cloud enforces:

```sql
CREATE UNIQUE INDEX uq_synced_events ON synced_events (edge_id, event_id);
```

`edge_id` is part of the key rather than trusting `event_id` to be globally
unique, so a misconfigured edge cloning another's database cannot corrupt a
neighbour's history.

### Batch ingest endpoint

```http
POST /api/v1/edges/{edge_id}/events
Content-Type: application/json

{ "events": [ … up to 500 … ] }
```

Response — **per-event results, HTTP 200 even with partial failure**:

```json
{
  "results": [
    { "event_id": "018f…20", "status": "accepted" },
    { "event_id": "018f…21", "status": "duplicate" },
    { "event_id": "018f…22", "status": "rejected", "error": "unknown kind" }
  ]
}
```

Design points:

- **`duplicate` is a success.** The edge marks the event synced and moves on.
  Returning an error for a replayed event would wedge the queue after every
  ambiguous timeout.
- **Per-event status, not batch-level.** One malformed event must not force the
  other 499 to be retried, and must not block the queue behind it. `rejected`
  events are quarantined at the edge for inspection.
- **HTTP 4xx only for a malformed request envelope** (bad JSON, bad `edge_id`,
  oversized batch). HTTP 5xx for genuine server faults — those are retried.

### Batch atomicity

Each batch is processed in **one transaction with `ON CONFLICT DO NOTHING`**
per event. If the transaction commits, every accepted event is durable. If it
fails, the edge retries the whole batch and the conflict clause makes the second
attempt harmless.

Rejected events are collected without aborting the transaction — they are never
inserted, so there is nothing to roll back.

### PostgreSQL schema

```sql
CREATE TABLE edge_instances (
    edge_id      TEXT PRIMARY KEY,
    display_name TEXT,
    first_seen_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    last_seen_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- The idempotency ledger. Every accepted event lands here first.
CREATE TABLE synced_events (
    id           BIGSERIAL PRIMARY KEY,
    edge_id      TEXT NOT NULL REFERENCES edge_instances(edge_id),
    event_id     UUID NOT NULL,
    kind         TEXT NOT NULL,
    occurred_at  TIMESTAMPTZ NOT NULL,
    received_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    payload      JSONB NOT NULL
);
CREATE UNIQUE INDEX uq_synced_events ON synced_events (edge_id, event_id);
CREATE INDEX idx_synced_kind_time ON synced_events (edge_id, kind, occurred_at DESC);

-- Projections, derived from synced_events. Every one carries edge_id.
CREATE TABLE devices (
    edge_id TEXT NOT NULL REFERENCES edge_instances(edge_id),
    device_id TEXT NOT NULL,
    name TEXT, firmware_version TEXT, status TEXT,
    last_seen_at TIMESTAMPTZ,
    PRIMARY KEY (edge_id, device_id)
);

-- No device_id: a plant reaches hardware through bindings (ADR-016), and the
-- cloud mirrors the edge's shape rather than inventing a simpler one.
CREATE TABLE plants (
    edge_id TEXT NOT NULL, plant_id TEXT NOT NULL,
    name TEXT, species TEXT, bindings_json JSONB, policies_json JSONB,
    PRIMARY KEY (edge_id, plant_id)
);

-- Narrow typed-kind projection, mirroring the edge (ADR-017).
CREATE TABLE measurements (
    edge_id     TEXT NOT NULL, device_id TEXT NOT NULL,
    point       TEXT NOT NULL DEFAULT 'default',
    kind        TEXT NOT NULL,
    occurred_at TIMESTAMPTZ NOT NULL,
    value_num   REAL, value_bool BOOLEAN,
    unit        TEXT NOT NULL, quality TEXT NOT NULL,
    sensor_id   TEXT, calibration_ref TEXT,
    batch_id    UUID, origin TEXT NOT NULL DEFAULT 'live',
    PRIMARY KEY (edge_id, device_id, point, kind, occurred_at)
);
CREATE INDEX idx_cloud_meas_batch ON measurements (edge_id, batch_id);

CREATE TABLE watering_events (
    edge_id TEXT NOT NULL, watering_event_id UUID NOT NULL,
    plant_id TEXT NOT NULL, mode TEXT NOT NULL,
    origin TEXT NOT NULL DEFAULT 'edge_command',  -- or offline_autonomous
    started_at TIMESTAMPTZ NOT NULL, completed_at TIMESTAMPTZ,
    requested_ml REAL, delivered_ml REAL, status TEXT NOT NULL,
    PRIMARY KEY (edge_id, watering_event_id)
);

CREATE TABLE device_events (
    edge_id TEXT NOT NULL, event_id UUID NOT NULL,
    device_id TEXT NOT NULL, kind TEXT NOT NULL, severity TEXT NOT NULL,
    detail JSONB, occurred_at TIMESTAMPTZ NOT NULL,
    PRIMARY KEY (edge_id, event_id)
);
```

**Two-layer design.** `synced_events` is the append-only ledger and the
idempotency boundary; the projection tables are derived views maintained in the
same transaction. This means:

- Replay is safe at the ledger level regardless of projection logic.
- A projection bug can be fixed and the tables rebuilt from `synced_events`
  without asking the edge to resend anything.
- `measurements` uses a natural composite PK so a re-projection is an upsert.
- Replayed offline history is just more events. A `watering.offline_autonomous`
  event forwarded after a device reconnects deduplicates on `(edge_id,
  event_id)` exactly like everything else, so a device that reconnects twice
  mid-replay creates no duplicate cloud rows (SAFETY-016).

The cost is storing measurement data twice (JSONB in the ledger, columns in the
projection). At V1 volumes this is megabytes, and the ability to rebuild is
worth more than the disk.

### Ordering

Events may arrive out of order — an outage drains oldest-first, but retries
interleave. Projections must therefore be **order-insensitive**:

- `measurements`: keyed by time, insertion order irrelevant.
- `devices.status`: guarded by `WHERE excluded.last_seen_at > devices.last_seen_at`
  so a late-arriving old status cannot overwrite a newer one.
- `watering_events`: keyed by id; `completed_at` fills in whenever it arrives.

This is why the edge does not need to guarantee ordered delivery, which in turn
is why the outbox can retry individual batches independently.

### Time on the wire

Cloud APIs use RFC 3339 strings (`"2026-08-25T11:30:00Z"`), unlike the MQTT
layer's integer milliseconds. HTTP APIs are read by humans and by charting code,
and PostgreSQL has a real `TIMESTAMPTZ`. The conversion happens once, in
`rhizo-cloud-client`.

## Alternatives considered

**State upserts instead of events.** Rejected: "current state" messages are
order-sensitive, so a delayed retry can overwrite newer data with older. Events
are order-insensitive by construction.

**A client-supplied `Idempotency-Key` HTTP header per request.** Rejected: it
deduplicates *requests*, not *events*, so a retry with a different batching
would slip through. Per-event ids are the correct granularity.

**Returning 409 for duplicates.** Rejected: it makes the most common
post-outage response an error, complicating client logic for no gain. Duplicate
is a normal, expected, successful outcome.

**Kafka or another log between edge and cloud.** Rejected as wildly
disproportionate. The outbox table *is* the durable log, and it is already
required for offline operation.

**Trusting `event_id` alone as globally unique.** Rejected: cheap insurance to
include `edge_id`, and it prevents one edge from corrupting another.

## Consequences

Positive:

- Replay after an arbitrarily long outage is safe and needs no special path.
- Partial batch failure degrades gracefully to per-event quarantine.
- Projections can be rebuilt from the ledger without device or edge involvement.

Negative, accepted:

- Measurement data is stored twice. Mitigated by ledger retention if it ever
  matters (not in V1).
- The cloud must know every event kind to project it. Unknown kinds are stored
  in the ledger and reported as `rejected` for projection purposes — the history
  is never lost even when the projection is not yet written.
- Two time representations (ms on MQTT, RFC 3339 on HTTP) is a real seam and a
  place bugs can hide. Mitigated by doing the conversion in exactly one crate
  and round-trip testing it (M7-011).

## Risks

- **Projection drift** between `synced_events` and the tables after a bug.
  *Mitigation:* a reprojection command (`cloud-api reproject --edge-id …`) and a
  consistency check comparing ledger counts to projection counts. Issue M7-012.
- **Batch size vs. request timeout** on a slow uplink: 500 events may not
  complete. *Mitigation:* the batch size is configurable and the client halves
  it on timeout, down to a floor of 10. Issue M7-007.
- **Clock disagreement** between edge and cloud makes `occurred_at` and
  `received_at` diverge. Accepted: `occurred_at` is edge-authoritative and the
  cloud never uses its own clock for anything but audit.
